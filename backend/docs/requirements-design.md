# Проект: требования клиники на сервере

Как требования [docs/requirements.md](../../docs/requirements.md) ложатся на архитектуру сервера
(VSA + DDD). Правила структуры — [architecture.md](architecture.md), термины —
[domain-model.md](domain-model.md), поля API — [api-contract.md](api-contract.md). Этот документ —
план: решения, слайсы, этапы и их статус. Сделанный этап отражается в глоссарии и контракте, а
здесь меняется только статус.

## Главные решения

1. **Три новых контекста** ([ADR-0008](adr/0008-rehab-alerts-access-contexts.md)):
   - **Реабилитация** `features.rehab` (основной) — программа, этапы, нормы, параметры наблюдения;
     правила тренировочной минуты, выполнения нормы, прогресса (ТР-01…ТР-03, ТР-05);
   - **Оповещения** `features.alerts` (поддерживающий) — журнал оповещений и проверки (ТР-08);
   - **Доступ** `features.access` (общий) — врачи, вход, сеансы, журнал доступа (ТР-11).

   Распределение пульса (ТР-04) и пульс по запросу (ТР-09) — в Мониторинге: в них нет норм
   пациента, это про пульс и «пульс сейчас».
2. **Контексты — слои:** `alerts → rehab → monitoring → patients → access`. Контекст
   импортирует только нижележащие (домен и `api.py`); нижний о верхних не знает. Проверяет
   import-linter.
3. **Хранить ввод, итоги считать.** В базе — минуты, программа с историей правок, оповещения,
   запросы пульса. Тренировочные минуты, выполнение нормы, прогресс и распределение пульса —
   чистые функции домена над минутами. Поздние минуты (ТР-03, п. 2) пересчитывать не нужно, а
   правила совпадают с телефоном на одних тестовых данных. Исключение — список пациентов
   (этап 6): там прогресс всех пациентов сразу, и итоги дней кешируются (`rehab_day_outcomes`,
   этап 7): подписчик `MinutesReceived` пересчитывает дни пришедших минут, сохранение плана
   сбрасывает итоги пациента, недостающие дни считаются при чтении.
4. **Правка программы — новая версия** ([ADR-0010](adr/0010-rehab-plan-revisions.md)):
   `RehabPlan` хранит версии `ProgramRevision` с днём начала действия. День оценивается версией,
   действовавшей в этот день (ТР-01, п. 8): правка не меняет прошлых итогов.
5. **Программа по умолчанию не записывается в базу.** Нет сохранённого плана —
   `RehabPlan.default_for(patient)`: один этап с нормами ТР-01, п. 5, с дня регистрации.
   Регистрация (контекст «Пациенты») о реабилитации не знает; план сохраняется при первой правке
   врачом. Так же получают программу пациенты, зарегистрированные до этого изменения.
6. **Реакция на принятые данные — через порт Мониторинга**
   ([ADR-0009](adr/0009-reactions-and-periodic-checks.md)). Мониторинг объявляет события
   `MinutesReceived`, `LiveHeartRateReceived` и порт подписчика `MonitoringSubscriber`; верхние контексты его
   реализуют, связывает `app`. Подписчики работают в транзакции приёма: «высокий пульс»
   (ТР-08) и кеш итогов дня (п. 3) не расходятся с минутами.
7. **Плановые дневные проверки — периодическая задача в процессе сервера** (ADR-0009): раз в минуту,
   без очереди и отдельного воркера. Идемпотентна (одно оповещение на «пациент, вид, день») и
   после перезапуска догоняет пропущенную проверку текущего дня.
8. **Телефону — опросом при синхронизации** (решено клиникой 2026-10-29): оповещения — по
   курсору `after`, активный запрос пульса — один на пациента, нормы — вместе с программой.
9. **Список пациентов собирает панель.** Строка ТР-06 состоит из данных трёх контекстов:
   пациенты и свежесть данных, прогресс, непросмотренные оповещения. Каждый контекст отдаёт свою
   часть списком по всем пациентам врача (три запроса, а не запрос на пациента); панель
   соединяет по `patient_id`. Общего «контекста панели», который знает всё, нет.
10. **Доступ к пациенту — в одном месте.** Эндпоинт панели получает пациента только через
    `features.patients.api.AttendedPatients` — он существует только при сеансе врача и отвечает
    `404` на чужого пациента. Тест обходит все маршруты `/patients/{patient_id}…` из OpenAPI и
    проверяет `404` от другого врача — новый эндпоинт без проверки не пройдёт тесты.
11. **Превышение тренировочных минут** (согласовано 2026-11-12): слайс
    `alerts/training_minutes`, подписчик `MinutesReceived` и реализация порта `rehab.domain.PlanChanged`,
    связанные только в `app`. После upsert — полный итог всех затронутых дней; при правке плана —
    сегодня в поясе пациента. Порог `training_minutes_upper_threshold` — 1–1440 или `null`,
    без автоматического медицинского значения; отсутствие в PUT сохраняет текущий порог.
    Исторические настройки дня, строгое превышение, только программа своей версии. Снимок первого
    превышения навсегда; не плановая проверка и не live, не блокирует вечерние виды и нижнюю норму.
    Минуты/план и оповещение — одна транзакция. Старому телефону — четыре прежних вида, новому —
    поддержанные через повторяемый `supported_kinds`, фильтр до пагинации. Колонка добавляется явной
    идемпотентной командой `app.schema_upgrade` без удаления базы; см. README.
12. **Каждое значение по умолчанию — одна константа** в домене своего контекста (правило 2
    требований). Значения В-21 помечены «пример, до выпуска к пациентам — ответ клиники».

## Правила, общие с телефоном

Тренировочная минута (ТР-02) и выполнение нормы дня (ТР-03) считаются и на сервере, и на
телефоне. Тестовые данные — критерии приёмки ТР-02 и ТР-03; те же случаи — в
`tests/features/rehab/domain/` и в Android-тестах этапа 4 (как `DailySummary` ↔
`DailySummaryTest`).

## Риски и что проверить

- **Скорость прогресса.** Прогресс одного пациента (карточка) считается по всем минутам прошедших
  дней программы (42 дня ≈ 60 000 минут) — для одного пациента допустимо. `GET /rehab-progress`
  читает кеш итогов дня: 500 пациентов на 42-й день программы — 0,53 с на машине разработчика
  (замер 2026-10-29, SQLite; `GET /patients` — 0,42 с). При первом открытии после правки плана
  дни пациента пересчитываются по минутам — один раз.
- **Значения по умолчанию В-21** (порог высокого пульса 130, «почти не ходит» 1 000 шагов, время
  17:00 UTC) — примеры из критериев, не медицинские рекомендации: до выпуска к пациентам — ответ
  клиники (`DEFAULT_MONITORING_SETTINGS`, одна константа).
- **Несколько процессов сервера.** Периодическая проверка в каждом процессе; дубликатов нет
  благодаря уникальности оповещения в базе. Дольше одного процесса на SQLite не планируется
  (ADR-0007).
- **Смена часового пояса пациента** меняет границы его дней. Версии программы хранят дату, а
  не момент; день оценивается по текущему поясу пациента.
