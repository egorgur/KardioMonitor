# ADR-0004: Домен на dataclasses, Pydantic — только на границе API

- Статус: предложено
- Дата: 2026-10-16

## Контекст

В FastAPI-проектах Pydantic-модели часто используют везде: как схему API, как доменный
объект и (через SQLModel) как таблицу. Тогда изменение формата JSON для телефона
меняет доменную модель и схему базы, а правила предметной области смешиваются с
настройками сериализации. В Android домен — чистый Kotlin без фреймворков.

## Решение

- Доменные типы — `@dataclass(frozen=True, slots=True)` из стандартной библиотеки,
  проверки — в `__post_init__` и фабриках, ошибка — `DomainRuleViolation` из
  `shared_kernel`. Порты — `typing.Protocol`.
- Pydantic — только в слайсах (`schemas.py`: контракт API), в `platform.web` (база схем
  `ApiModel`, `ProblemDetail`) и в `app/settings.py`. Схема переводит себя в домен
  (`to_domain()`) и обратно (`from_domain()`).
- SQLAlchemy — только в `data/` и `platform/db`; репозиторий переводит строки в доменные типы.
- import-linter запрещает домену импортировать `pydantic`, `fastapi`, `sqlalchemy`.

## Последствия

- Домен читается и тестируется без фреймворков; его правила можно сверить с Android.
- Контракт API и схема базы меняются независимо от домена.
- Есть код перевода между схемой, доменом и таблицей — это осознанная цена, перевод
  держится рядом со схемой и в репозитории.
- Формат проверяет Pydantic (тип, наличие поля, часовой пояс), правила — домен; ошибки
  обоих превращаются в `422` с `problem+json`.

## Отвергнутые варианты

- Pydantic-модели как доменные объекты — домен зависит от библиотеки сериализации,
  правила смешиваются с настройками JSON.
- SQLModel — одна модель на API, домен и таблицу.
- attrs — лишняя зависимость при наличии `dataclasses`.
