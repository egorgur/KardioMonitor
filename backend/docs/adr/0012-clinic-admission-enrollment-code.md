# ADR-0012: Пациент от клиники — карточка отдельной таблицей, телефон по одноразовому коду

- Статус: принято (2026-10-29)
- Дата: 2026-10-29

## Контекст

ТР-07: врач создаёт пациента, вводит ФИО, дату рождения и биопараметры; телефон пациента
должен привязаться к этой карточке без ввода имени — через QR v2 (`e=` в
[android/docs/qr-contract.md](../../../android/docs/qr-contract.md)). ФИО и диагноз — особая
категория персональных данных: видит только лечащий врач, в журналы не попадают. Таблицу
`patients` без миграций (ADR-0007) расширить нельзя, а в ней обязательный отпечаток токена.

## Решение

- **Имя пациента = ФИО** («Фамилия Имя Отчество», части по 1–32 знака — помещаются в
  `PatientName`). Список, поиск (ТР-06) и экран телефона работают одинаково для пациентов от
  клиники и зарегистрированных с телефона по имени.
- **Карточка** (`PatientProfile`: ФИО по частям, дата рождения, рост, вес, диагноз) — таблица
  `patient_profiles`, читается только эндпоинтом карточки (`profile_of`), не при каждом запросе.
  Доменные типы карточки скрывают значения в `repr`.
- **Пациент от клиники получает токен-заглушку** (случайный, никому не выдаётся): колонка
  обязательна. Привязка телефона заменяет отпечаток токена.
- **Код привязки** `EnrollmentCode` — 128 бит, base64url (без `;` и 32 hex подряд — правило
  QR-контракта), в базе только SHA-256, действует 72 ч, гасится атомарно один раз
  (`UPDATE … RETURNING`). Новый код удаляет прежние непогашенные. Ошибка одна —
  `422 invalid_enrollment_code` (неизвестный, погашенный, истёкший — не различаются).
- Сервер **не строит QR**: ключа браслета у него нет (открытый вопрос 2). QR v2 собирает утилита
  персонала из ключа браслета и кода `e=`.
- **Параметры запросов к базе не попадают в журнал** ни при каком уровне: `hide_parameters=True`
  и уровень `aiosqlite` не ниже INFO (`platform.db.provider.create_engine`). Найдено тестом
  «в журнале нет ФИО»: на уровне DEBUG aiosqlite писал запросы с параметрами.
- Создание пациента, открытие карточки и выдача кода пишутся в журнал доступа (ТР-11, п. 6).

## Последствия

- Привязка на новом телефоне новым кодом отключает прежний телефон (`401` по старому токену).
- Регистрация по имени с телефона (демо, В-10) остаётся; такого пациента назначает врачу
  администратор.
- Перед реальными пациентами (PostgreSQL, ADR-0002) — колонку токена сделать необязательной и
  убрать заглушку, карточку — шифровать на уровне хранения по решению о 152-ФЗ.

## Отвергнутые варианты

- ФИО полями таблицы `patients` — нужна миграция, и ФИО читалось бы при каждом запросе телефона.
- Код из 6 цифр — удобно вводить руками, но перебирается; код идёт в QR, вводить его не нужно.
- Сервер строит QR целиком — пришлось бы хранить ключ браслета на сервере.
