# ADR-0006: Архитектурные проверки — import-linter и pytest

- Статус: предложено
- Дата: 2026-10-16

## Контекст

Правила VSA и DDD ([architecture.md](../architecture.md)) не должны держаться только на
тексте: агент надёжнее следует падающей проверке. В Python нет модификаторов видимости,
и любой модуль может импортировать любой другой.

## Решение

- **import-linter** (`uv run lint-imports`), контракты в `pyproject.toml`: слои
  `app → features → platform → shared_kernel`; домен без `fastapi`, `pydantic`,
  `sqlalchemy`, `platform`; независимость слайсов; запрет прямого импорта `data` и
  `sqlalchemy` из слайсов.
- **ruff** — механические правила кода (размер и сложность функций, async, даты без пояса,
  `print`, `assert`, голые `except`).
- **pytest** `tests/architecture/` — то, чего нет в инструментах: длина модуля ≤ 300
  строк, пустые суффиксы имён классов, запрещённые имена модулей (`utils.py`), кириллица
  в именах тестов `features/`.
- Сообщение о падении называет правило, файл и строку. Всё входит в полную проверку и
  в Stop-hook агента.

## Последствия

- Нарушение границ ломает проверку, а не ждёт ревью.
- Новый слайс нужно добавить в контракты import-linter — это делает skill `/new-slice`;
  забытый слайс не проверяется на независимость (ревью и `architecture-reviewer` это ловят).
- import-linter — зависимость только для разработки.

## Отвергнутые варианты

- Только ревью — правила нарушаются незаметно.
- Самописный разбор `import` в pytest (как в Android, ADR-0005 там) — import-linter
  уже умеет косвенные импорты и внешние пакеты, свой разбор пришлось бы поддерживать.
- Отдельные пакеты (дистрибутивы) на контекст — избыточно для одного сервера.
