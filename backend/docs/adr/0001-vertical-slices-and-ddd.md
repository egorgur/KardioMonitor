# ADR-0001: Vertical Slice Architecture + DDD

- Статус: принято
- Дата: 2026-10-16

## Контекст

Бэкенд принимает данные браслетов с телефонов пациентов и отдаёт их клинике. Он
развивается в основном ИИ-агентом, как и Android-приложение. Агенту нужно находить весь
код сценария в одном месте и менять его, не задевая другие сценарии. Предметная область
будет расти: доступ сотрудников, целевые зоны пульса, тренировки.

## Решение

Код организуется по ограниченным контекстам (`features.monitoring`, `features.patients`)
и внутри них — по вертикальным слайсам, по одному на сценарий (обычно — эндпоинт или
группа эндпоинтов одного сценария). Правила предметной области живут в доменных типах на
языке из [domain-model.md](../domain-model.md), общем с Android-приложением. Подробно —
[architecture.md](../architecture.md).

## Последствия

- Для задачи достаточно прочитать один слайс и домен его контекста.
- Термины и правила совпадают с Android: одно понятие `ActivityMinute` по обе стороны API.
- Небольшое дублирование между слайсами допустимо (отдельные схемы запросов); общий код
  выносится, когда дублирование стало реальным.
- Структура отличается от привычной для FastAPI раскладки `routers/ schemas/ services/
  models/` — агенту нужно следовать документам проекта, а не шаблонам из интернета.

## Отвергнутые варианты

- Слои `routers/ schemas/ services/ crud/` на всё приложение — сценарий размазан по
  четырём папкам, изменения задевают чужой код.
- Пакеты «по доменам» без слайсов (`monitoring/router.py`, `monitoring/service.py`) — с
  ростом контекста `router.py` и `service.py` становятся свалкой всех сценариев.
- Микросервисы на контекст — избыточно для одного сервера и одной базы.
