# Работа с ИИ-агентом

Как ставить задачи агенту (Claude Code и аналогам) и как агенту их выполнять в бэкенде.
Основано на [рекомендациях Anthropic по Claude Code](https://code.claude.com/docs/en/best-practices)
и [документации по CLAUDE.md](https://code.claude.com/docs/en/memory). Процесс совпадает
с Android-проектом ([android/docs/ai-agent-workflow.md](../../android/docs/ai-agent-workflow.md)).

## Главные принципы

1. **Контекст — главный ресурс.** Чем больше агент прочитал лишнего, тем хуже он
   следует правилам. Поэтому код организован слайсами: для задачи нужна одна папка и
   домен её контекста.
2. **У задачи должна быть проверка.** Тест, `lint-imports`, ответ `curl`. Без проверки
   агент останавливается, когда работа «выглядит готовой».
3. **Сначала разобраться, потом план, потом код.** Особенно если задача меняет контракт
   API, схему базы или затрагивает несколько контекстов.
4. **Правила, которые можно проверить автоматически, должны проверяться автоматически**
   (ruff, mypy, import-linter, тесты, hooks), а не только описываться текстом.

## Цикл задачи

```
Разобраться → План → Реализация → Проверка → Документы → Ревью → Коммит
```

| Шаг | Что делает агент | Результат |
|---|---|---|
| Разобраться | Читает `backend/CLAUDE.md`, нужный раздел `docs/`, код **одного** слайса и домен контекста. Широкий поиск — через подагента | Понимание, где менять |
| План | Для задач на несколько файлов — план в режиме планирования: какие слайсы, доменные типы, эндпоинты, миграции, тесты | Согласованный план |
| Реализация | Код по [coding-rules.md](coding-rules.md) внутри слайса; правила — в домене; схема БД — миграцией | Изменения |
| Проверка | Полная проверка из [testing.md](testing.md), включая тесты `db` | Вывод команд как доказательство |
| Документы | Глоссарий, карта слайсов, контракт API, ADR — если изменились | Актуальные `docs/` |
| Ревью | Свежий взгляд: подагент `architecture-reviewer` (границы, домен, правила) и `/code-review` (ошибки) по `git diff` | Список проблем по существу |
| Коммит | Только по просьбе человека. Репозиторий общий на `KardioMonitor/`: в коммит — только файлы задачи (`git add backend/…`), без `.env`, дампов базы и данных пациентов | — |

Пропускать план можно, если изменение описывается одним предложением
(переименование, текст ошибки, константа).

## Как ставить задачу агенту

Шаблон:

```
Контекст: <контекст и слайс, напр. monitoring/daily_summary>
Задача: <что должно появиться/измениться для клиента API>
Правила предметной области: <например, «день считается в часовом поясе пациента»>
Контракт: <эндпоинт, поля запроса/ответа, коды ошибок — или «без изменений»>
Готово, когда:
  - <проверяемый критерий 1, напр. тест `test_итоги_дня_не_учитывают_минуты_другого_дня_пациента`>
  - <критерий 2, напр. `curl ... /daily-summaries?from=...` возвращает 7 дней>
Вне задачи: <что не трогать>
```

Плохо: «сделай API для врача».
Хорошо: «Добавь слайс `monitoring/daily_summary`: `GET /api/v1/patients/{patient_id}/daily-summaries?from=&to=`,
не больше 92 дней, день — в часовом поясе пациента. `DailySummary.of` — с теми же
правилами, что в Android (`android/.../DailySummary.kt`). Тесты: дни без минут не
возвращаются; минута 23:59 по Новосибирску попадает в свой день, а не в следующий по UTC;
период 93 дня → 422 `period_too_long`. Проверка: полная проверка из testing.md».

Для больших функций попросите агента сначала **проинтервьюировать вас** и записать
спецификацию в `docs/specs/<название>.md`, а реализацию начинать в новой сессии.

## Чего агенту не делать без явного согласования

- Ломать контракт `v1` ([api-contract.md](api-contract.md)): удалять и переименовывать
  поля, менять смысл, ужесточать ограничения.
- Удалять колонки или таблицы с данными пациентов, редактировать применённые миграции,
  запускать `alembic downgrade` или `DROP` на базе, отличной от тестовой.
- Подключаться к базе сервера (не разработки и не тестовой) и выполнять там что-либо.
- Логировать или коммитить токены, `.env`, `DATABASE_URL` с паролем, ключи браслета,
  данные пациентов (включая выгрузки для отладки).
- Принимать решения из «открытых вопросов» [domain-model.md](domain-model.md) — хранение ФИО,
  ключа браслета, способ входа.
- Добавлять библиотеки (нужен ADR) и повышать нижние границы версий без причины.
- Делать широкий рефакторинг «заодно».

## Управление контекстом (Claude Code)

- `/clear` между несвязанными задачами.
- Исследование кода и поиск в интернете — через подагентов: они читают много, а в
  основной контекст возвращают выводы.
- После двух неудачных исправлений одного и того же — `/clear` и новая, более точная
  постановка с учётом выясненного.
- `CLAUDE.md` короткий (< 200 строк); подробности — в `docs/` и читаются по ссылке.
- **Запускать Claude Code из `backend/`**, а не из корня репозитория. Git общий на
  `KardioMonitor/`, но настройки агента у каждого проекта свои: `backend/.claude/`
  подхватываются, только когда `backend/` — рабочий каталог.

## Skills, подагенты и hooks проекта (создаются вместе с каркасом)

По образцу `android/.claude/`. Повторяющиеся сценарии описаны один раз — агент не
восстанавливает порядок шагов из нескольких документов.

| Что | Когда |
|---|---|
| `/new-slice <контекст>/<слайс>` | Новый сценарий: папка слайса, `router.py`, схемы, сценарий, фейки, тесты, подключение в `app/routers.py`, контракты import-linter |
| `/api-change` | Любое изменение эндпоинта: проверка совместимости по api-contract.md, снимок OpenAPI |
| `/db-migration <что>` | Изменение схемы: таблица в `data/tables.py`, автогенерация, ручная правка, `upgrade`/`downgrade` на тестовой базе |
| подагент `architecture-reviewer` | Ревью диффа на соответствие architecture.md, domain-model.md, coding-rules.md, api-contract.md |

| Hook | Что делает |
|---|---|
| `Stop` → `checks-on-stop.sh` | Если `.py`, `pyproject.toml` или `uv.lock` менялись после последнего зелёного прогона — запускает `ruff check`, `mypy`, `lint-imports`, `pytest -m "not db"` и не даёт завершить ход, пока они падают |
| `PreToolUse(Bash)` → `guard-patient-data.sh` | Блокирует `alembic downgrade`, `DROP`/`TRUNCATE`, `psql` к адресу не из списка разработки, вывод `.env` и переменных с токенами |

Hook не заменяет проверку: тесты `db` и полная проверка перед завершением задачи
запускаются вручную. Личные настройки — в `.claude/settings.local.json` (не в git).

## Внешние skills

Сторонний skill — это текст, который агент будет выполнять: **перед установкой прочитать
`SKILL.md`**, после установки — закоммитить его в `backend/.claude/skills/`, чтобы версия
была зафиксирована. Правила проекта ([architecture.md](architecture.md),
[coding-rules.md](coding-rules.md)) **главнее** сторонних skills: если skill советует
иначе (папки `routers/ services/ models/` на всё приложение, `BaseRepository[T]`,
`dependency-injector`, синхронный SQLAlchemy, моки вместо фейков, SQLite в тестах
репозиториев), следуйте документам проекта.

| Skill | Источник | Когда подключать |
|---|---|---|
| `vertical-slice-architecture` | [mryll/skills](https://github.com/mryll/skills) | Фон для [architecture.md](architecture.md) |
| `test-namer` | mryll/skills | Имена тестов по В. Хорикову |
| `domain-driven-design` | [booklib-ai/booklib](https://github.com/booklib-ai/booklib) | Моделирование новых контекстов (доступ, реабилитация) |

Установка (из `backend/`, сначала прочитать `SKILL.md` в репозитории):

```bash
npx skills add mryll/skills --skill vertical-slice-architecture
npx skills add mryll/skills --skill test-namer
npx skills add booklib-ai/booklib --skill domain-driven-design
```

Skills по FastAPI из каталогов (skills.sh и подобные) не устанавливаются без ревью:
их практики собраны и приведены в соответствие с проектом в [coding-rules.md](coding-rules.md).
