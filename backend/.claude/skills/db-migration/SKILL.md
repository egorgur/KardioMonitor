# Изменение схемы базы: $ARGUMENTS

Таблицы — данные пациентов. Потерянную колонку не восстановить.

## 1. Определить режим

```bash
grep -n alembic pyproject.toml || echo "Alembic не подключён — режим демо (ADR-0007)"
```

## 2а. Демо: SQLite, `create_all` (сейчас)

1. Правка — в `features/<контекст>/data/tables.py` (`Mapped[...]`, `mapped_column`,
   `UtcDateTime` для времени). Новая таблица — в `app/db_metadata.py`.
2. Репозиторий и тест репозитория (`tests/features/<контекст>/data/`, настоящая SQLite).
3. `create_all` не меняет существующие таблицы. Сказать человеку: демо-базу `kardio.db`
   нужно пересоздать (остановить сервер, удалить `kardio.db*`), — и **не удалять её самому**:
   на ней могут быть данные телефона. После этого телефон регистрируется заново.
4. `./scripts/check.sh`.

## 2б. PostgreSQL + Alembic (после ADR о переходе)

1. Правка `tables.py`, затем автогенерация:
   ```bash
   uv run alembic revision --autogenerate -m "<что меняется>"
   ```
2. **Прочитать и поправить миграцию руками:** автогенерация не видит переименования
   (делает drop + add), серверные значения по умолчанию, данные. Удаление колонки или
   таблицы с данными пациентов — только с согласия человека.
3. На базе разработки: `upgrade head` → `downgrade -1` → `upgrade head`. `downgrade` и
   `psql` — только к localhost (hook блокирует остальное).
4. Применённую миграцию не редактировать — новая миграция поверх.
5. `./scripts/check.sh` (тесты `-m db` — на PostgreSQL).

## 3. Документы

если меняется подход к хранению.
