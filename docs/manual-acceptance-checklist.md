# KardioMonitor — полный чек-лист ручной приёмки

Документ проверяет работающую систему на соответствие [требованиям клиники](requirements.md):
сервер `backend/`, панель врача `frontend/`, Android-приложение пациента `android/` и настоящий
Xiaomi Mi Smart Band 6. Это ручная приёмка поверх автоматических тестов, а не их замена.

## Как фиксировать результат

Для каждого сценария отметить один статус:

- [ ] **PASS** — ожидаемый результат получен полностью.
- [ ] **FAIL** — результат отличается; приложить описание и номер дефекта.
- [ ] **BLOCKED** — проверка невозможна; указать внешнюю причину.
- [ ] **N/A** — сценарий официально исключён из объёма приёмки; приложить решение.

Карточка прогона:

| Поле | Значение |
|---|---|
| Дата и время | |
| Проверяющий | |
| Git commit / описание сборки | |
| Backend URL | |
| Браузер и версия | |
| Телефон, Android API | |
| Версия APK | |
| Mi Band и прошивка | |
| База данных / тестовый набор | |
| Итог PASS / FAIL / BLOCKED | |

Для каждого FAIL сохранить: шаг, фактический результат, ожидаемый результат, снимок экрана или
обезличенный фрагмент журнала, `X-Request-ID`, устройство и время. Не прикладывать пароли,
сессионные cookie, токены телефона, ключ браслета, полный QR-код, реальные ФИО и диагнозы.

## 1. Подготовка стенда

- [ ] **P-01. Тестовые данные вымышлены.** Используются только фиктивные ФИО, дата рождения и
  диагноз. В логах, снимках и сетевых дампах нет данных настоящего пациента.
- [ ] **P-02. Backend.** Сервер запущен с отдельной SQLite-базой, периодические проверки включены,
  `/health` отвечает `200`, Swagger доступен по `/docs`.
- [ ] **P-03. Frontend.** Панель открывается с того же backend или через Vite proxy; API и панель
  используют один согласованный стенд.
- [ ] **P-04. Учётные записи.** Созданы врачи `doctor.a` и `doctor.b` с разными паролями длиной не
  меньше 12 символов.
- [ ] **P-05. Пациенты.** Есть пациент врача A, пациент врача B, пациент без врача и набор для
  проверки поиска. Их UUID записаны в закрытом протоколе прогона.
- [ ] **P-06. Устройство.** APK установлен через `adb install -r`, данные приложения не очищены,
  телефон разблокирован, Bluetooth включён.
- [ ] **P-07. Браслет.** Известны корректные MAC и 32-символьный auth key. Mi Fitness и Zepp Life
  не удерживают BLE-соединение.
- [ ] **P-08. Время.** Время сервера и телефона синхронизировано; известен часовой пояс пациента.
- [ ] **P-09. Уведомления.** Зафиксировано исходное состояние разрешения уведомлений и каналов
  Android, чтобы затем проверить разрешённый и запрещённый варианты.
- [ ] **P-10. Доказательства.** Подготовлены обезличенные HTTP-логи, `adb logcat` с тегами
  `KardioBLE`, `KardioServer`, `KardioReminder`, снимки экрана и запросы к тестовой базе.

## 2. Базовая работа браслета и передача данных

### M-01. Привязка настоящего Mi Band 6

**Требования:** исходный функционал, основа ТР-02, ТР-03 и ТР-09.

- [ ] Отсканировать корректный QR v1 или вручную ввести MAC и ключ.
- [ ] Выдать требуемые разрешения Bluetooth; на Android 8–11 дополнительно проверить запрос
  геолокации.
- [ ] Подключиться к браслету.
- [ ] Убедиться, что показаны заряд, шаги и успешная авторизация Huami 2021.
- [ ] Перезапустить приложение: привязка сохранена, повторный ввод ключа не требуется.
- [ ] Проверить журналы: ключ браслета и персональные данные не выведены.

### M-02. Ошибки привязки

- [ ] Неверный формат QR не приводит к падению и не сохраняется.
- [ ] Неверный MAC и неверный формат ключа дают понятную ошибку.
- [ ] Ключ правильной длины, но неправильного значения, приводит к отказу авторизации.
- [ ] Отказ в Bluetooth-разрешении объяснён пользователю.
- [ ] Занятый Mi Fitness браслет даёт понятное состояние недоступности.
- [ ] После каждой ошибки прежняя рабочая привязка не повреждена.

### M-03. Частота пульса и ручная синхронизация

- [ ] Выбрать частоту измерения пульса 1 минута.
- [ ] Походить с надетым браслетом и выполнить «Синхронизировать».
- [ ] На телефоне появились новые минуты, шаги, пульс и тип активности.
- [ ] Повторная синхронизация без новых данных не создаёт дубликаты.
- [ ] После завершения короткого сеанса BLE-соединение освобождено.

### M-04. Выгрузка на сервер

- [ ] Зарегистрированный телефон отправляет новые минуты после синхронизации.
- [ ] Повторная отправка тех же минут идемпотентна.
- [ ] Серверный курсор не пропускает новые минуты и не просит уже подтверждённые данные.
- [ ] При недоступном сервере история остаётся локально и уходит после восстановления связи.

## 3. ТР-11 — врачи, вход и разграничение доступа

### M-05. Создание врача администратором

- [ ] Пароль короче 12 символов отклоняется без создания врача.
- [ ] Врач с допустимым логином, именем и паролем создаётся.
- [ ] Повтор того же логина отклоняется без изменения существующей записи.
- [ ] Пароль вводится скрыто, не передаётся аргументом команды и не попадает в shell history.

### M-06. Вход и выход

- [ ] Корректные логин и пароль открывают панель; показано имя вошедшего врача.
- [ ] Регистр логина нормализуется: вариант `Doctor.A` входит в `doctor.a`.
- [ ] Cookie имеет `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/api`.
- [ ] После «Выйти» прежняя cookie больше не авторизует API.
- [ ] Обновление страницы после выхода показывает форму входа, а не данные пациента.

### M-07. Неверный пароль и блокировка

- [ ] Неизвестный логин и неверный пароль существующего логина возвращают одинаковое сообщение.
- [ ] Пять неверных попыток подряд приводят к блокировке на 15 минут.
- [ ] Правильный пароль во время блокировки возвращает `429`, не снимая блокировку.
- [ ] Административный `reset-password` задаёт новый пароль и снимает блокировку.

### M-08. Истечение сеанса

- [ ] Зафиксировать сеанс без запросов более 8 часов либо воспроизвести эквивалент на тестовом
  стенде с управляемыми часами.
- [ ] Следующий API-запрос возвращает `401 session_required`.
- [ ] Панель возвращается к форме входа и не показывает устаревшие данные пациента.

### M-09. Изоляция пациентов врачей

- [ ] Врач A видит в списке только назначенных ему пациентов.
- [ ] Врач A напрямую запрашивает UUID пациента B: профиль, день, план, прогресс, оповещения,
  запрос пульса — каждый endpoint возвращает `404 patient_not_found`.
- [ ] Ответ на чужой UUID не отличается от ответа на случайный несуществующий UUID.
- [ ] Старый общий `X-Dashboard-Key` не даёт доступа без сессии врача.

### M-10. Назначение и передача пациента

- [ ] Пациент без врача отсутствует в панелях A и B.
- [ ] После административного назначения пациент появляется только у выбранного врача.
- [ ] После передачи от A к B пациент исчезает у A и появляется у B.
- [ ] Существующие медицинские данные пациента при передаче не теряются.

### M-11. Журнал доступа

- [ ] Открыть профиль и план, изменить план, выпустить код привязки и создать пациента.
- [ ] В `access_records` есть врач, действие, субъект и время для предусмотренных операций.
- [ ] В записях нет ФИО, даты рождения, диагноза, пароля, cookie и токенов.

## 4. ТР-07 — создание и привязка пациента

### M-12. Создание валидной карточки

- [ ] Врач вводит вымышленные фамилию, имя, отчество, дату рождения, рост, вес, диагноз и часовой
  пояс.
- [ ] Пациент создаётся один раз, появляется в списке врача и получает программу по умолчанию.
- [ ] Создавший врач становится лечащим.
- [ ] Код привязки показан врачу и имеет срок действия.
- [ ] После обновления страницы профиль совпадает с введёнными значениями.

### M-13. Валидация карточки

Каждый случай проверить отдельно; после ошибки список и база не должны содержать частичного
пациента.

- [ ] Нет фамилии.
- [ ] Нет имени.
- [ ] Дата рождения в будущем.
- [ ] Возраст меньше 18 или больше 120 лет.
- [ ] Рост меньше 100 или больше 250 см.
- [ ] Вес меньше 30 или больше 300 кг.
- [ ] Пустой либо чрезмерно длинный диагноз.
- [ ] Неизвестный часовой пояс IANA.
- [ ] Сервер возвращает понятную ошибку, введённые поля формы не теряются без необходимости.

### M-14. Жизненный цикл enrollment-кода

- [ ] Первый обмен действующего кода на телефоне успешен.
- [ ] Повторное использование того же кода отклоняется как `invalid_enrollment_code`.
- [ ] Выпуск нового кода немедленно отменяет прежний.
- [ ] Код старше 72 часов отклоняется.
- [ ] Новый enrollment другого телефона отзывает прежний upload token пациента.

### M-15. Полный QR v2

- [ ] Сформировать QR `kardio;<MAC>;<KEY>;s=https://<server>;e=<code>` из тестовых значений.
- [ ] Сканирование сначала обменивает enrollment-код, затем сохраняет привязку браслета.
- [ ] Телефон не просит ввести имя пациента и использует карточку сервера.
- [ ] После перезапуска сохранены и сервер, и браслет.
- [ ] HTTP вместо HTTPS, испорченный/повторный код, недоступный сервер и ошибка сохранения не
  заменяют прежнюю рабочую конфигурацию частично.

> **Известный пробел:** штатная staff-утилита выпуска QR v2 ещё не реализована; строгий
> clinic workflow ТР-07.4 остаётся BLOCKED. Для проверки контракта QR составляется вручную.

## 5. ТР-06 — список пациентов и поиск

### M-16. Содержимое строки пациента

- [ ] Показаны ФИО.
- [ ] Показаны день и прогресс программы.
- [ ] Показано выполнение нормы за сегодня либо корректное отсутствие данных.
- [ ] Показана свежесть последней истории.
- [ ] Свежий «пульс сейчас» отображается отдельно от истории.
- [ ] Показано число непросмотренных оповещений.
- [ ] Автоматический polling обновляет значения без перезагрузки страницы.

### M-17. Поиск

- [ ] Для `Иванов Пётр`, `Иванова Анна`, `Петров Иван` запрос `иван` находит всех троих.
- [ ] Поиск не зависит от регистра.
- [ ] Запрос `семенов` находит `Семёнов`.
- [ ] Подстрока в имени, фамилии и отчестве работает одинаково.
- [ ] Пустой поиск возвращает полный доступный врачу список.
- [ ] Чужие пациенты не появляются ни в результатах, ни в подсказках.

### M-18. Производительность 500 пациентов

- [ ] Подготовить 500 пациентов одного врача с реалистичным прогрессом и оповещениями.
- [ ] Измерить `GET /patients`, `GET /rehab-progress`, `GET /alerts/unviewed-counts` не менее 20
  раз после прогрева.
- [ ] Каждый ответ укладывается в 1 секунду на согласованном стенде.
- [ ] Зафиксировать p50, p95 и максимум; интерфейс остаётся отзывчивым при поиске и выборе.

## 6. ТР-01 — программа, этапы и нормы

### M-19. Программа по умолчанию

- [ ] У нового пациента программа начинается в день регистрации и длится 42 дня.
- [ ] Один этап покрывает дни 1–42.
- [ ] Целевая зона 90–110 уд/мин, 30 тренировочных минут, 10 000 шагов.
- [ ] Порог ходьбы 60 шагов/мин.
- [ ] Значения одинаковы на сервере, в панели и после синхронизации на телефоне.

### M-20. Несколько этапов

- [ ] Создать программу 25 дней с этапами 1–15 и 16–25 и разными нормами.
- [ ] День 15 использует первый этап; день 16 — второй.
- [ ] Панель и телефон показывают одинаковый номер этапа и нормы.

### M-21. Редактирование программы

- [ ] Изменить длительность, диапазон, минуты, шаги и параметры наблюдения.
- [ ] «Добавить этап» делит диапазон без дыр и пересечений.
- [ ] «Удалить этап» присоединяет дни к соседнему этапу без потери покрытия.
- [ ] Итоговое резюме формы совпадает с сохранённым ответом API.

### M-22. Валидация программы и атомарность

Каждый невалидный вариант должен оставить прежнюю программу без изменений.

- [ ] Пропуск дней между этапами.
- [ ] Пересечение этапов.
- [ ] Этап выходит за конец программы.
- [ ] Первый день больше последнего.
- [ ] Диапазон пульса 120–100.
- [ ] Граница пульса вне 40–220.
- [ ] Длительность вне 1–365 дней.
- [ ] Тренировочные минуты вне 1–1440.
- [ ] Шаги вне 0–100 000.
- [ ] Порог ходьбы вне 1–250.
- [ ] Порог высокого пульса вне 60–250.

### M-23. Историческая версия программы

- [ ] На 10-й день программы сохранить новую норму вместо 30 минут — 40 минут.
- [ ] Дни 1–9 продолжают оцениваться по 30 минутам.
- [ ] День 10 и последующие оцениваются по 40 минутам.
- [ ] Перезапуск сервера не меняет выбор версии для прошлого дня.

### M-24. Время дневных оповещений

- [ ] Для пациента UTC+3 настройка 17:00 UTC показана как 20:00 у пациента.
- [ ] Редактор сохраняет UTC-время без сдвига при повторном открытии.
- [ ] Смена часового пояса пациента корректно меняет локальную подпись.

### M-25. Кэш программы на Android

- [ ] Телефон получает новую программу после синхронизации.
- [ ] При недоступном сервере последняя успешная программа остаётся доступной.
- [ ] После убийства процесса и повторного открытия программа восстановлена.
- [ ] Ошибка обновления не стирает кэш и не подменяет владельца данных.

## 7. ТР-02 и ТР-03 — тренировочные минуты и норма дня

### M-26. Матрица тренировочной минуты

При зоне 90–110 и пороге ходьбы 60 сервер и телефон должны дать одинаковый результат.

- [ ] 80 шагов, пульс 100 — тренировочная минута.
- [ ] 80 шагов, пульс 90 — тренировочная, нижняя граница включена.
- [ ] 80 шагов, пульс 110 — тренировочная, верхняя граница включена.
- [ ] 61 шаг, пульс 100 — тренировочная.
- [ ] 60 шагов, пульс 100 — не ходьба.
- [ ] 80 шагов, пульс 115 — ходьба выше зоны.
- [ ] 80 шагов без пульса — ходьба без измеренного пульса.
- [ ] 80 шагов при `not_worn` — не ходьба.
- [ ] 80 шагов при `charging` — не ходьба.
- [ ] При пороге 40: 50 шагов и пульс 100 — тренировочная.

### M-27. Комбинации нормы дня

- [ ] 15 тренировочных минут и 6 200 шагов — норма не выполнена.
- [ ] 36 непоследовательных тренировочных минут и 10 500 шагов — выполнена.
- [ ] 40 тренировочных минут и 9 000 шагов — не выполнена.
- [ ] 20 тренировочных минут и 12 000 шагов — не выполнена.
- [ ] В шаги дня входят все шаги, а не только шаги тренировочных минут.
- [ ] Результаты сервера, панели и телефона совпадают.

### M-28. Пустой, текущий и неполный день

- [ ] День без минут показывает «нет данных», а не нулевое выполнение.
- [ ] Текущий день явно помечен предварительным.
- [ ] Ходьба без пульса показана отдельным количеством и процентом.
- [ ] Есть подсказка про измерение пульса раз в минуту.
- [ ] После прихода поздних минут итог обновляется.

### M-29. Часовые границы дня

- [ ] Минута 23:59 относится к предыдущему локальному дню пациента.
- [ ] Минута 00:00 относится к следующему локальному дню.
- [ ] Поздняя выгрузка предыдущего дня пересчитывает предыдущий, а не день загрузки.
- [ ] Одинаковые UTC-моменты правильно отображаются в часовом поясе пациента.

## 8. ТР-04 — распределение пульса

### M-30. Расчёт интервалов за день

Для пульса `39, 45, 50, 52, 58, 120, 135`:

- [ ] `< 40` — 1 минута.
- [ ] `40–49` — 1 минута.
- [ ] `50–59` — 3 минуты.
- [ ] `120+` — 2 минуты.
- [ ] Остальные интервалы — 0.
- [ ] Сумма интервалов равна числу минут с измеренным пульсом.
- [ ] Минуты без пульса не попадают ни в один интервал.

### M-31. Визуализация

- [ ] Цвет точки дневного графика совпадает с цветом соответствующего интервала.
- [ ] Целевая зона пациента выделена.
- [ ] Отсутствующее значение оставляет разрыв, а не рисуется как ноль.
- [ ] Tooltip показывает время пациента и правильный пульс.
- [ ] График и список читаемы на десктопе и телефоне.

### M-32. Недостающие агрегаты

- [ ] **BLOCKED:** распределение за неделю отсутствует.
- [ ] **BLOCKED:** распределение за всю программу отсутствует.

> Это известный пробел предположения ТР-04.4. Решение клиники В-08 должно либо подтвердить
> необходимость реализации, либо исключить эти два пункта из приёмки.

## 9. ТР-05 — прогресс реабилитации

### M-33. Программа в процессе

- [ ] На 12-й день 42-дневной программы показано «день 12 из 42».
- [ ] Если выполнены 9 из 11 завершённых дней, показано «9 из 11».
- [ ] Текущий день входит в прошедшие дни, но не в знаменатель завершённых суток.
- [ ] Текущий этап и его диапазон показаны верно.
- [ ] Список пациентов, карточка и Android показывают одинаковые числа.

### M-34. Статусы дней и завершение

- [ ] Выполненный, невыполненный, без данных, текущий и будущий день визуально различаются.
- [ ] День без данных не смешан с обычным невыполненным днём.
- [ ] После последнего дня показано «программа завершена» и N из M выполненных.
- [ ] Изменение исторической версии плана не переписывает старые статусы.

## 10. ТР-08 — оповещения

### M-35. Эпизод высокого пульса из истории

При пороге 130 загрузить 135, 140, 138 в 10:01–10:03, обычные значения в 10:04–10:05 и 131 в
10:06.

- [ ] Создано одно оповещение длительностью 6 минут и максимумом 140.
- [ ] Значение ровно 130 не считается превышением.
- [ ] Повторная выгрузка тех же минут не создаёт дубликат.
- [ ] В тексте нет диагноза или медицинского заключения.

### M-36. Высокий пульс из live readings

- [ ] Серия live-значений создаёт оповещение.
- [ ] Продолжение в пределах допустимого разрыва обновляет то же alert ID.
- [ ] Новый максимум и длительность видны врачу.
- [ ] Обновлённое оповещение снова становится непросмотренным, но не дублируется.

### M-37. Дневные оповещения

- [ ] В 17:00 UTC при 12 минутах и 6 200 шагах создано `daily_target_missed`.
- [ ] При 400 шагах дополнительно создано одно `low_activity`.
- [ ] При 35 минутах и 11 000 шагах создано `daily_target_met`, без missed/low activity.
- [ ] Повтор периодической проверки не создаёт дубликаты.
- [ ] Проверка до заданного времени не создаёт дневное оповещение.
- [ ] Дневные оповещения создаются только внутри программы; высокий пульс — независимо от неё.

### M-38. Перезапуск и поздние данные

- [ ] Сервер выключен в момент дневной проверки и после запуска догоняет её один раз.
- [ ] Поздние минуты обновляют итог дня, но не создают второе дневное оповещение.
- [ ] Перезапуск не дублирует уже существующие alert ID.

### M-39. Журнал врача

- [ ] Общая лента содержит оповещения всех пациентов врача, новые сверху.
- [ ] Журнал пациента содержит только его оповещения.
- [ ] Фильтры всех четырёх видов работают.
- [ ] Непросмотренные счётчики в общей навигации и строке пациента совпадают.
- [ ] «Просмотрено» уменьшает счётчики, но не удаляет запись.
- [ ] Чужие оповещения врачу недоступны.

### M-40. Доставка пациенту

- [ ] После синхронизации оповещение появляется в локальном списке Android.
- [ ] При разрешённых уведомлениях появляется системное уведомление нужного канала.
- [ ] Обновление того же alert ID меняет локальные факты без второго уведомления.
- [ ] При запрещённых уведомлениях запись всё равно доступна внутри приложения.
- [ ] После выдачи разрешения ранее не показанное оповещение уведомляется один раз.

### M-41. Текст и задержка

- [ ] Врач и пациент видят фактические значения и пороги.
- [ ] Указана задержка синхронизации 30–60 минут.
- [ ] Указано, что система не заменяет экстренную помощь.
- [ ] Текст не звучит как диагноз или медицинское заключение.

> **До выпуска:** значения В-21 (130 уд/мин, 1 000 шагов, 17:00 UTC) и пациентские тексты В-19
> требуют письменного одобрения клиники.

### M-41a. Верхний порог тренировочных минут

**Требование:** [ТР-08, п. 12](requirements.md#тр-08-оповещения).

- [ ] У нового пациента проверка отключена; врач задаёт 60 мин/сутки отдельно от целевой нормы.
- [ ] 59 и 60 тренировочных минут за день не вызывают превышение; 61 создаёт одно оповещение
  сразу после загрузки, до окончания суток и независимо от времени дневных оповещений.
- [ ] Повтор пакета, рост до 70 минут и перезапуск сервера не создают дубль и не изменяют факт 61
  и порог 60 в историческом оповещении. Отметка просмотра не сбрасывается.
- [ ] Поздние и исправленные минуты проверяют полный итог своего дня в часовом поясе пациента.
- [ ] Снижение порога ниже сегодняшнего факта создаёт оповещение сразу после сохранения плана,
  если его ещё нет; прошлые дни остаются на прежних настройках.
- [ ] Пустое поле отключает проверку, 0/1441/дробь не сохраняются. Старый PUT без нового поля
  не сбрасывает уже назначенный порог.
- [ ] Превышение видно в обоих журналах врача, фильтре и счётчике. Вечерняя проверка других
  дневных оповещений не пропускается; выполнение нижней нормы не отменяется.
- [ ] Обновлённый Android получает новый вид и показывает одно системное уведомление и запись
  в журнале. Повторная синхронизация и перезапуск приложения не уведомляют повторно.
- [ ] Старый Android продолжает получать прежние виды без ошибки неизвестного `kind`;
  пагинация не теряет последующие доступные ему оповещения.
- [ ] Существующая база обновляется без удаления данных; повторное обновление безопасно.

## 11. ТР-09 — пульс по запросу врача

### M-42. Подготовка Android

- [ ] В приложении подтверждена обычная CDM-ассоциация с точным MAC браслета.
- [ ] `adb shell cmd companiondevice list 0` показывает ассоциацию `ru.kardiomonitor`.
- [ ] Разрешены уведомления и канал запроса пульса.
- [ ] В manifest есть `connectedDevice`, нет `REQUEST_COMPANION_SELF_MANAGED`.

### M-43. Успешный запрос

- [ ] Врач создаёт запрос на 10 минут.
- [ ] Панель показывает «Ожидает телефон» и предупреждение о следующей синхронизации.
- [ ] После ручной синхронизации состояние становится «Измерение идёт».
- [ ] На телефоне видно постоянное уведомление с действием «Остановить».
- [ ] Экран погашен; значения продолжают приходить на общий график каждые 2–3 секунды.
- [ ] Через 10 минут состояние «Измерение завершено», Worker и уведомление исчезли.
- [ ] Ручной и клинический режимы не создают два одновременных BLE-потока.

### M-44. Остановка пациентом

- [ ] Запустить новый запрос и нажать «Остановить» в уведомлении.
- [ ] Измерение и Worker прекращаются, уведомление исчезает.
- [ ] Панель показывает «Остановлено пациентом».
- [ ] При временном отсутствии сети терминальный статус сохраняется и отправляется после связи.

### M-45. Валидация и конфликт

- [ ] Длительность 1 и 60 минут принимается.
- [ ] 0, дробное значение и 61 отклоняются в панели и API.
- [ ] Пока запрос waiting/running, второй запрос возвращает конфликт и не создаётся.
- [ ] После терминального состояния новый запрос разрешён.
- [ ] Ожидающий запрос старше 2 часов становится failed/expired и больше не блокирует новый.

### M-46. Причины отказа

Проверить отдельно; скрытого BLE-измерения быть не должно.

- [ ] Запрещены уведомления — `notification_permission_denied`.
- [ ] Нет CDM association — `companion_association_missing`.
- [ ] Браслет выключен/занят — `band_unavailable`.
- [ ] Ошибка измерения — `measurement_failed`.
- [ ] Истёкший запрос — `expired`.
- [ ] Панель переводит каждый код в понятный русский текст.

### M-47. Перезапуск во время запроса

- [ ] Убить процесс или перезагрузить телефон без очистки данных.
- [ ] Повторно запускается не больше одного уникального Worker.
- [ ] Выполняется только оставшееся время, а не полная длительность заново.
- [ ] В outbox сохраняется порядок `running` перед терминальным статусом.
- [ ] Сервер в итоге получает одно согласованное терминальное состояние.

## 12. ТР-10 — локальные напоминания

### M-48. Настройки по умолчанию

- [ ] «Пора пройтись» включено: интервал 1 час, порог 250 шагов.
- [ ] «Норма дня» включена: время 18:00.
- [ ] «Наденьте браслет» выключено.
- [ ] Дневное окно 09:00–20:00 и дни недели показаны.
- [ ] Настройки сохраняются после перезапуска и не требуют сервера.

### M-49. «Пора пройтись»

- [ ] Полный интервал с 120 шагами показывает одно напоминание.
- [ ] Интервал с 900 шагами не показывает напоминание.
- [ ] Неполные данные интервала не приводят к ложному напоминанию.
- [ ] Сон внутри интервала подавляет напоминание.
- [ ] Вне дневного окна и в выключенный день уведомления нет.
- [ ] Для 30 минут порог пропорционально равен половине часового.

### M-50. «Норма дня» и «Наденьте браслет»

- [ ] После заданного времени невыполненная норма показывает оставшиеся минуты и шаги.
- [ ] Выполненная норма не показывает дневное напоминание.
- [ ] Полный час `not_worn` может показать «Наденьте браслет» при включённом виде.
- [ ] Полный час `charging` не считается снятым браслетом.
- [ ] После выполнения нормы подавлены и прогулочное, и дневное напоминание до конца дня.

### M-51. Действия и ограничения

- [ ] «Отложить на 30 мин» подавляет этот вид на 30 минут.
- [ ] «Не напоминать сегодня» подавляет все виды до следующего локального дня.
- [ ] Девятое напоминание за день не показывается при максимуме 8.
- [ ] Выключенный системный канал конкретного вида остаётся тихим.
- [ ] Отключение всех локальных напоминаний не отключает оповещения клиники.

### M-52. Перезапуск, часовой пояс и фон

- [ ] WorkManager восстанавливает проверки после перезагрузки.
- [ ] Изменение часового пояса переносит окно на новое локальное время.
- [ ] Exact alarm permission не требуется.
- [ ] В режиме энергосбережения нет серии дубликатов после задержанного запуска.
- [ ] Зафиксировать фактическую задержку periodic work относительно ожидаемого времени.

> **Риск приёмки:** реализация использует 15-минутную периодическую rolling-проверку. Клиника
> должна подтвердить допустимую точность относительно примера «около конца интервала».

## 13. Надёжность, offline, фон и приватность

### M-53. Фоновая синхронизация

- [ ] Погасить экран и отправить приложение в фон.
- [ ] Плановый Worker открывает короткий BLE-сеанс, получает историю и закрывает соединение.
- [ ] При наличии сети минуты отправляются на сервер.
- [ ] При Doze допустимая системная задержка не приводит к потере или дублям.

### M-54. Длительный offline

- [ ] Отключить сервер/сеть, продолжать носить браслет и выполнять синхронизации.
- [ ] История и локальный прогресс доступны без сервера.
- [ ] Напоминания работают offline.
- [ ] После восстановления сети выгрузка продолжается с server cursor дневными пакетами.
- [ ] План, оповещения и запросы обновляются после следующей синхронизации.

### M-55. Перезапуск Android

- [ ] После убийства процесса сохранены браслет, регистрация клиники, план, история, оповещения,
  настройки напоминаний и pending outbox.
- [ ] Данные одного patient ID не показываются после регистрации другого пациента.
- [ ] Уникальные фоновые работы не дублируются.

### M-56. Перезапуск backend

- [ ] После рестарта с той же базой сохранены врачи, пациенты, профили, планы, минуты,
  оповещения, запросы пульса, сессии и журнал доступа.
- [ ] Периодические проверки возобновлены.
- [ ] Дневные и high-HR оповещения не дублируются.

### M-57. Секреты Android

- [ ] Band auth key и server token в SharedPreferences представлены шифротекстом.
- [ ] Старые открытые значения после миграции удалены.
- [ ] Keystore key нельзя экспортировать.
- [ ] Backup/data extraction rules исключают перенос секретов.
- [ ] Логи не содержат ключ, токен, QR и персональные данные.

### M-58. Секреты backend

- [ ] Пароли — Argon2id hashes, не plaintext.
- [ ] Session token, upload token и enrollment code хранятся fingerprint/hash, а не открыто.
- [ ] Ошибки API не возвращают stack trace.
- [ ] Логи не содержат ФИО, дату рождения, диагноз, пароль, cookie и токены.
- [ ] Диагноз в React выводится как текст, не исполняет HTML/JavaScript.

### M-59. Валидация API и retry

- [ ] Naive timestamp и невалидное время отклоняются.
- [ ] Отрицательные шаги и пульс вне 11–249 отклоняются.
- [ ] Неизвестные поля, слишком большой пакет и полностью невалидный пакет не сохраняются
  частично.
- [ ] Повтор минуты идемпотентен.
- [ ] `4xx` использует стабильный problem `code` и не повторяется бесконечно телефоном.
- [ ] Network/`5xx` сохраняет данные для последующего retry.
- [ ] Каждый ответ содержит `X-Request-ID` для корреляции.

### M-60. Недоступность сервера в панели

- [ ] При первом открытии без backend показано «Сервер недоступен».
- [ ] После уже загруженных данных ошибка polling не очищает экран молча, а помечает данные
  устаревшими.
- [ ] После восстановления backend polling возвращается к актуальным данным.
- [ ] Повтор polling не повторяет POST-действия врача.

## 14. Сквозные пользовательские сценарии

### E2E-01. Клиника создаёт пациента до первого дня наблюдения

- [ ] Врач A создаёт карточку пациента.
- [ ] Телефон сканирует вручную сформированный QR v2 и привязывает браслет.
- [ ] Пациент включает измерение раз в минуту, синхронизирует и отправляет историю.
- [ ] Пациент виден только врачу A.
- [ ] Телефон и панель показывают одинаковые итоги дня, нормы, прогресс и часовой пояс.

### E2E-02. Изменение плана и одинаковый прогресс

- [ ] Врач меняет нормы с текущего дня.
- [ ] Телефон получает новую программу при синхронизации.
- [ ] На одинаковом наборе минут Android и backend совпадают по тренировочным минутам, шагам,
  выполнению нормы и минутам ходьбы без пульса.
- [ ] Прошлые дни сохраняют прежнюю версию норм.

### E2E-03. Оповещение высокого пульса у врача и пациента

- [ ] На сервер приходит тестовый эпизод высокого пульса.
- [ ] В журнале и счётчике врача появляется одно оповещение.
- [ ] После синхронизации тот же alert ID появляется в Android-списке и системном уведомлении.
- [ ] Повтор данных и обновление эпизода не создают дубль.

### E2E-04. Запрос пульса с погашенным экраном

- [ ] Врач создаёт запрос на 10 минут.
- [ ] Телефон получает его после синхронизации и показывает foreground notification.
- [ ] При погашенном экране панель продолжает получать значения.
- [ ] Первый запуск завершается автоматически; второй останавливается пациентом.
- [ ] Панель показывает правильные терминальные состояния обоих запросов.

### E2E-05. Длительная недоступность и восстановление

- [ ] Отключить backend при работающих телефоне и браслете.
- [ ] Накопить историю, дождаться локальных напоминаний, перезапустить телефон.
- [ ] Убедиться, что локальные данные и настройки сохранились.
- [ ] Вернуть backend: история выгружается идемпотентно, план и оповещения обновляются, pending
  статусы отправляются.
- [ ] Итоги телефона и панели сходятся после завершения синхронизации.

## 17. Финальное решение о приёмке

- [ ] Все обязательные сценарии имеют PASS.
- [ ] Каждый FAIL связан с зарегистрированным дефектом и решением о блокировке выпуска.
- [ ] Каждый BLOCKED связан с владельцем и сроком снятия блокировки.
- [ ] Все неблокирующие предположения из требований либо приняты клиникой, либо явно оставлены
  вне выпуска.
- [ ] Обезличенные доказательства сохранены и позволяют повторить вывод.
- [ ] Итог подписан представителем клиники, разработчиком Android, backend/frontend и
  ответственным за приватность данных.
