# Требования клиники к KardioMonitor

Формальная запись устных требований клиники (исходник — `D.md` в корне репозитория) и ответов
клиники на вопросы по ним. Документ для людей и ИИ-агентов: что должна делать система, как
проверить, что сделано, и что ещё не решено.

> Статус документа: **в согласовании** (ответы клиники от 2026-10-29 внесены). Статус каждого
> требования — в таблице «Статусы». Код пишется только по требованиям «готово к работе»; перед
> кодом — контракт API, глоссарии и, если нужно, ADR.

## Как читать

- **ДОЛЖНА / НЕ ДОЛЖНА** — обязательное поведение. **Решено** — ответ клиники (с датой).
  **Предположение** — толкование автора записи со ссылкой на вопрос `В-NN`.
- Каждое требование: `ТР-NN`, исходная фраза из `D.md`, формулировка, критерии приёмки
  («Дано / Когда / Тогда»), затронутые части системы.
- Части системы: **Сервер** — `backend/`, **Панель** — `frontend/` (панель клиники),
  **Телефон** — `android/` (приложение пациента).
- Числа в критериях — примеры для теста, если не сказано иное.

### Правила для ИИ-агента

1. Реализовывать только требования со статусом «готово к работе». Вопрос `В-NN` с пометкой
   «блокирует» — спросить человека; толкование самостоятельно не выбирать.
2. Предположение по неблокирующему вопросу реализуется как записано. Каждое настраиваемое
   значение и каждое значение по умолчанию — в одном месте (константа домена или настройка),
   чтобы ответ клиники менял одну строку.
3. Новые понятия — сначала в глоссарии контекста (`backend/docs/domain-model.md`,
   `android/docs/domain-model.md`), имена — из раздела «Термины» ниже.
4. Новые поля и эндпоинты — сначала `backend/docs/api-contract.md`, потом код.
5. Правила, которые считаются и на сервере, и на телефоне (тренировочная минута, выполнение
   нормы), — одинаковые, с тестом на одинаковых данных с обеих сторон, как `DailySummary`
   (`test_daily_summary.py` ↔ `DailySummaryTest`).
6. Тексты панели и приложения НЕ ДОЛЖНЫ звучать как медицинское заключение или диагноз:
   данные браслета бытовые (`backend/docs/domain-model.md`). Система не экстренная служба.
   Тексты оповещений пациенту утверждает врач (В-19).
7. Данные пациентов — особая категория персональных данных (152-ФЗ): правила
   `backend/docs/coding-rules.md`, раздел 13. ФИО, дата рождения и диагноз — не в логах, не в
   тестовых данных (только вымышленные).

## Исходное состояние (что уже есть)

| Часть | Есть сейчас |
|---|---|
| Телефон | Поминутная история с браслета: шаги, пульс (если измерен), тип активности (`снят`, `зарядка`, `сон`, `другое` + сырой код), интенсивность (не расшифрована). Фоновая синхронизация раз в ~30 мин. «Пульс сейчас» — по кнопке пациента, значение каждые 2–3 с. Частоту фонового пульса выбирает пациент (1–120 мин) |
| Сервер | Регистрация пациента **с телефона** по имени; приём минут и «пульса сейчас»; итоги дня (шаги, пульс ср/мин/макс, покрытие пульсом, минуты без браслета) |
| Панель | Список пациентов, «пульс сейчас», итоги дня, графики пульса по минутам и шагов по часам. Вход — общий ключ панели, учётных записей врачей нет (так было до ТР-11; с 2026-10-29 — аккаунты врачей) |

Ограничения, важные для всех требований:

- **Задержка данных.** Минуты попадают на сервер при синхронизации: обычно через 30–60 мин
  после записи, а если телефон далеко от браслета или выключен — позже. В реальном времени
  (секунды) — только «пульс сейчас».
- **Пульс есть не в каждой минуте.** Браслет меряет пульс с выбранной частотой; для
  тренировочных минут нужна частота **1 минута** (корневой `README.md`, раздел 3).
- **Ходьбу браслет явно не помечает.** Коды типа активности для ходьбы не расшифрованы
  (`kind_code` 1, 80, 90… сохраняются как есть). Ходьба определяется по шагам за минуту (ТР-02).
- **Связь только от телефона к серверу.** **Решено 2026-10-29:** всё, что сервер передаёт
  телефону (нормы, оповещения, запросы пульса), телефон забирает при синхронизации. Push
  (Firebase) пока не используется.

## Термины

Предлагаемые имена для контекста «Реабилитация» (`features.rehab` на сервере, запланирован в
`backend/docs/domain-model.md`). Утвердить при переносе в глоссарий.

| Термин | Имя в коде | Определение |
|---|---|---|
| Программа реабилитации | `RehabProgram` | Курс пациента: дата начала, длительность в днях, этапы. У каждого пациента своя |
| День программы | `ProgramDay` | Номер дня пациента от начала программы: 1, 2, … Дни — по часовому поясу пациента (`PatientDay`) |
| Этап программы | `RehabStage` | Отрезок программы «дни N–M» со своими нормами дня. Этапы идут подряд и покрывают всю программу |
| Нормы дня | `DailyTargets` | Нормы этапа: зона тренировочного пульса, тренировочных минут в день, шагов в день |
| Зона тренировочного пульса | `TrainingHeartRateZone` | Диапазон пульса `[нижняя, верхняя]` уд/мин, границы включительно |
| Параметры наблюдения | `MonitoringSettings` | Настройки пациента, общие для всей программы: порог ходьбы, порог высокого пульса, порог «почти не ходит», время дневных оповещений |
| Порог ходьбы | `walking_steps_threshold` | Шагов за минуту, **больше** которых минута считается минутой ходьбы. По умолчанию 60 |
| Минута ходьбы | `WalkingMinute` (правило) | Браслет надет и шагов за минуту больше порога ходьбы |
| Тренировочная минута | `TrainingMinute` (правило) | Минута ходьбы, в которой пульс измерен и лежит в зоне тренировочного пульса |
| Выполнение нормы за день | `DailyTargetProgress` | Тренировочных минут из нормы, шагов из нормы, выполнена ли норма дня |
| Прогресс реабилитации | `RehabProgress` | Сколько дней программы прошло и в скольких из них норма дня выполнена |
| Распределение пульса | `HeartRateDistribution` | Сколько минут пульс был в каждом интервале 10 уд/мин |
| Оповещение | `PatientAlert` | Запись в базе сервера о событии у пациента. Видят врач и пациент. **Не путать с напоминанием** |
| Напоминание | `Reminder` | Уведомление на телефоне, которое пациент настраивает сам. Не хранится на сервере, врачу не видно |
| Запрос пульса в прямом режиме | `LiveHeartRateRequest` | Команда врача: телефону пациента включить «пульс сейчас» на N минут |
| Карточка пациента | `PatientProfile` | ФИО, дата рождения, биопараметры — вводит клиника при создании пациента |
| Биопараметры | `BodyParameters` | Рост, вес, диагноз; список дополняется (В-06) |
| Врач | `Clinician` | Сотрудник клиники с аккаунтом на панели. Видит только своих пациентов (контекст «Доступ», `features.access`) |
| Лечащий врач пациента | `attending_clinician` | Врач, которому принадлежит пациент: его пациента видит только он |

## Требования

### ТР-01. Нормы пациента и программа реабилитации

> «настройки диапазонов для человека индивидуальные; правила 30 мин в день чсс 90-110 шаги
> 10.000 шагов в сутки»

**Решено 2026-10-29:**
- Длительность программы у каждого пациента своя.
- Врач делит программу на этапы со своими нормами (например, дни 1–15 — одни нормы, 16–25 —
  другие).
- Порог ходьбы, порог высокого пульса, порог «почти не ходит» и время дневных оповещений
  настраиваются для каждого пациента и имеют значения по умолчанию.

1. У каждого пациента ДОЛЖНА быть программа реабилитации `RehabProgram`: дата начала (день 1)
   и длительность в днях (1–365 — *предположение, В-02*). У нового пациента программа начинается в
   день регистрации и длится 42 дня (*предположение, В-02*).
2. Программа ДОЛЖНА состоять из этапов `RehabStage`. Этап — «дни N–M» и нормы дня:
   - зона тренировочного пульса: нижняя и верхняя граница, уд/мин;
   - тренировочных минут в день;
   - шагов в день.
3. Этапы ДОЛЖНЫ идти подряд без пропусков и пересечений и покрывать программу от дня 1 до
   последнего. Нарушение — понятная ошибка («дни 16–17 не входят ни в один этап»), программа не
   меняется.
4. У пациента ДОЛЖНЫ быть параметры наблюдения `MonitoringSettings` (на всю программу):

   | Параметр | По умолчанию | Используется |
   |---|---|---|
   | Порог ходьбы, шагов в минуту | 60 | ТР-02 |
   | Порог высокого пульса, уд/мин | В-21 | ТР-08 |
   | Порог «почти не ходит», шагов в день | В-21 | ТР-08 |
   | Верхний порог тренировочных минут за сутки, мин | `null` — отключён | ТР-08, п. 12 |
   | Время дневных оповещений, UTC | В-21 | ТР-08 |

5. Новому пациенту ДОЛЖНЫ назначаться: один этап на всю программу с нормами **90–110 уд/мин,
   30 тренировочных минут, 10 000 шагов** и параметры наблюдения по умолчанию.
6. Врач ДОЛЖЕН на панели менять длительность программы, этапы, нормы этапов и параметры
   наблюдения.
7. Проверки при сохранении (*предположение, В-02*): зона `40 ≤ нижняя < верхняя ≤ 220`;
   тренировочных минут в день 1–1440; шагов в день 0–100 000; порог ходьбы 1–250 шагов в
   минуту; порог высокого пульса 60–250 уд/мин.
8. Изменения ДОЛЖНЫ действовать с текущего дня. Прошедшие дни оцениваются нормами, которые
   действовали в тот день; их итог правка не меняет. *Предположение (В-02).*
9. Телефон ДОЛЖЕН получать с сервера нормы текущего дня и порог ходьбы при синхронизации — для
   показа выполнения нормы пациенту (ТР-03).

Части системы: Сервер (хранение, проверки, API), Панель (форма программы и параметров),
Телефон (получение норм).

Критерии приёмки:
- Дано новый пациент. Тогда у него один этап на всю программу: 90–110, 30 мин, 10 000 шагов;
  порог ходьбы 60.
- Дано программа 25 дней, этапы «1–15» и «16–25». Когда открыт день 16. Тогда нормы второго этапа.
- Дано этапы «1–15» и «18–25». Когда врач сохраняет. Тогда ошибка «дни 16–17 не входят ни в
  один этап», программа прежняя.
- Дано врач ввёл зону 120–100. Тогда ошибка «нижняя граница должна быть меньше верхней».
- Дано сегодня день 10, врач поменял норму этапа «1–15» с 30 на 40 мин. Тогда дни 1–9 оценены
  по 30 мин, дни 10–15 — по 40.

### ТР-02. Тренировочные минуты

> «Когда человек идёт (категория деятельности) у него должен БЫТЬ тренирующий пульс в
> диапазоне x-y.»

**Решено 2026-10-29:** тренировочная минута — минута, в которую пульс в зоне тренировочного
пульса и пациент шагал больше заданного порога. Порог ходьбы свой у каждого пациента, по
умолчанию 60.

1. **Минута ходьбы:** браслет надет (тип не `снят` и не `зарядка`) и шагов за минуту **больше**
   порога ходьбы пациента (ТР-01). Ровно порог — не ходьба.
2. **Тренировочная минута:** минута ходьбы, пульс в ней измерен и лежит в зоне тренировочного
   пульса дня (границы включительно).
3. Минута ходьбы с пульсом вне зоны — «ходьба выше зоны» или «ходьба ниже зоны»; без пульса —
   «пульс не измерен». Такие минуты НЕ ДОЛЖНЫ считаться тренировочными.

Части системы: Сервер (правило в домене `rehab`), Телефон (то же правило).

Критерии приёмки (зона 90–110, порог ходьбы 60):
- 80 шагов, пульс 100 → тренировочная.
- 80 шагов, пульс 90 → тренировочная (граница зоны включительно).
- 61 шаг, пульс 100 → тренировочная; 60 шагов, пульс 100 → не ходьба.
- 80 шагов, пульс 115 → ходьба выше зоны.
- 80 шагов, пульса нет → ходьба, пульс не измерен.
- Браслет снят → не ходьба.
- Порог ходьбы пациента 40: 50 шагов, пульс 100 → тренировочная.

### ТР-03. Выполнение нормы за день

> «Указание насколько человек выполнил свою норму на день (вы держали шаги и пульс нужными 15
> минут из 30) Считаем»

**Решено 2026-10-29:**
- В норме дня два показателя: тренировочные минуты (ТР-02) и, отдельно, шаги за день.
- Тренировочные минуты считаются по отдельности и суммируются за день; идти подряд не обязаны.
- Если к концу суток не выполнена норма тренировочных минут **или** норма шагов — норма дня не
  выполнена.
- Для подсчёта выполнения нормы граница дня — конец суток.

1. Для каждого дня пациента система ДОЛЖНА считать:
   - тренировочных минут: факт и норма дня («15 из 30 мин»);
   - шагов за день (все шаги дня, не только в минуты ходьбы): факт и норма («6 200 из 10 000»);
   - выполнена ли норма дня: тренировочных минут ≥ нормы **и** шагов ≥ нормы.
2. День — сутки пациента в его часовом поясе (`PatientDay`, 00:00–24:00). Окончательный итог —
   по всем минутам этих суток. Минуты, пришедшие после полуночи (поздняя синхронизация),
   пересчитывают итог своего дня.
3. Пока сутки не закончились — итог «пока»: «15 из 30 мин, день не закончился».
4. Доля минут дня без пульса ДОЛЖНА показываться рядом с итогом: если пульс мерялся редко,
   «15 из 30» может быть занижено. Подсказка: «включите измерение пульса раз в минуту».
5. Итог ДОЛЖЕН показываться врачу на панели (день пациента) и пациенту в приложении. Телефон
   считает итог сам по своей истории (без ожидания синхронизации) по нормам с сервера (ТР-01).

Части системы: Сервер (расчёт, API дня), Панель, Телефон.

Критерии приёмки (нормы 30 мин и 10 000 шагов):
- 15 тренировочных минут, 6 200 шагов → «15 из 30 мин», «6 200 из 10 000», не выполнена.
- 36 тренировочных минут (3 отрезка по 12), 10 500 шагов → выполнена.
- 40 тренировочных минут, 9 000 шагов → не выполнена (не хватает шагов).
- 20 тренировочных минут, 12 000 шагов → не выполнена (не хватает минут).
- За день нет минут → «нет данных», норма не выполнена.
- Минуты 23:00–23:59 пришли в 07:00 следующего дня → итог прошлого дня пересчитан.

### ТР-04. Распределение пульса по интервалам

> «отображение статистики: в какие врем промеж были пульс в диапазоне 40-50 50-60 … 120+»

1. Для дня пациента система ДОЛЖНА показывать, сколько минут пульс был в каждом интервале:
   `< 40`, `40–49`, `50–59`, …, `110–119`, `120+` (левая граница включительно, шаг 10 уд/мин).
2. Учитываются только минуты с измеренным пульсом. Сумма по интервалам = число минут с пульсом.
3. *Предположение (В-08):* «в какие временные промежутки» — нужно видеть и **когда** пульс был в
   интервале: на графике пульса дня интервалы различаются цветом, зона пациента выделена.
4. *Предположение (В-08):* кроме дня — то же за неделю и за всю программу.

Части системы: Сервер (расчёт), Панель (диаграмма и раскраска графика).

Критерии приёмки:
- Пульс 45, 52, 58, 120, 135 → `40–49`: 1, `50–59`: 2, `120+`: 2, остальные 0.
- Пульс 39 → `< 40`: 1. Пульс 50 → `50–59`.

### ТР-05. Прогресс реабилитации

> «Прогресс бар у прохождения пациентами реабилитации»

**Решено 2026-10-29:** прогресс — сколько дней программы прошло и в скольких из них выполнена
норма, заданная врачом этому пациенту. Программа и её этапы у каждого пациента свои (ТР-01).

1. Система ДОЛЖНА показывать:
   - **прошло дней:** «день 12 из 42» — полоса прогресса;
   - **норма выполнена:** «в 9 днях из 11» — среди **завершённых** суток программы, по нормам
     этапа каждого дня (ТР-03);
   - текущий этап: «этап 2: дни 16–25».
2. Текущий день входит в «прошло», но не в счёт выполненных, пока сутки не закончились.
   *Предположение (В-01).*
3. День без данных — норма не выполнена, на панели помечен «нет данных». *Предположение (В-01).*
4. После последнего дня программы: «программа завершена: норма выполнена в N днях из M».

Части системы: Сервер (расчёт), Панель (список и карточка пациента), Телефон (показ пациенту).

Критерии приёмки (программа 42 дня с 01.10, сегодня 12.10):
- «день 12 из 42».
- Норма выполнена 01.10–09.10, не выполнена 10.10 и 11.10 → «в 9 днях из 11».
- Сегодня 20.11 → «программа завершена: норма выполнена в N днях из 42».

### ТР-06. Главная страница: все пациенты, поиск, прогресс

> «главная со всеми пациентами поиск прогресс»

1. Главная страница панели ДОЛЖНА показывать всех пациентов вошедшего врача (ТР-11).
2. ДОЛЖЕН быть поиск по ФИО (подстрока в любой части ФИО, без учёта регистра и `ё`/`е`). До ТР-07
   — по имени, которое ввёл пациент.
3. В строке пациента ДОЛЖНЫ быть: ФИО, прогресс реабилитации (ТР-05), выполнение нормы за
   сегодня (ТР-03), когда пришли последние данные, число непросмотренных оповещений (ТР-08).
4. Список ДОЛЖЕН работать при 500 пациентах: ответ сервера ≤ 1 с. *Предположение (В-09).*

Части системы: Панель, Сервер (`GET /api/v1/patients` — новые поля и поиск).

Критерии приёмки:
- Пациенты «Иванов Пётр», «Иванова Анна», «Петров Иван»; ввод «иван» → все трое.
- Пациент «Семёнов»; ввод «семенов» → найден.

### ТР-07. Создание пациента клиникой

> «создать пациента вводим всю информацию»

**Решено 2026-10-29:**
- При создании пациента вводятся ФИО, дата рождения и биопараметры: рост, вес, диагноз.
  Полный список биопараметров уточняется.
- Данные хранятся в базе данных на сервере.

1. Врач ДОЛЖЕН создавать пациента на панели, заполняя карточку пациента. Создавший врач
   становится лечащим врачом пациента (ТР-11). Карточка:
   - фамилия, имя (обязательно), отчество (если есть);
   - дата рождения (не в будущем; возраст 18–120 лет — *предположение*);
   - рост, см (100–250 — *предположение*);
   - вес, кг (30–300 — *предположение*);
   - диагноз — текст. Код МКБ-10 или свободный текст — В-06 (пока текст).
2. Список биопараметров ДОЛЖЕН расширяться без переделки карточки: новый параметр — новое поле
   в схеме и миграция, без изменения уже введённых данных.
3. При создании ДОЛЖНЫ задаваться программа и этапы (ТР-01); по умолчанию — значения ТР-01.
4. После создания система ДОЛЖНА выдать способ привязать телефон пациента к этой карточке без
   ввода имени на телефоне: QR v2 с одноразовым кодом (`android/docs/qr-contract.md`, этап 2
   утилиты персонала `android/docs/staff-app/README.md`).
5. Карточка хранится в базе сервера. ФИО, дату рождения и диагноз видит только лечащий врач
   пациента (ТР-11); в журналы сервера они НЕ ДОЛЖНЫ попадать; телефон пациента получает только
   то, что нужно для его экранов.
6. Самостоятельная регистрация с телефона по имени (демо) — В-10.

Зависимость: ТР-11 (аккаунты врачей). Показывать ФИО и диагноз по общему ключу панели нельзя.

Части системы: Сервер, Панель, Телефон (сканирование QR v2), утилита персонала.

Критерии приёмки:
- Врач заполнил ФИО, дату рождения, рост, вес, диагноз и сохранил → пациент в списке (ТР-06)
  с программой по умолчанию и QR для привязки телефона.
- Дата рождения в будущем → ошибка, пациент не создан.
- Без фамилии → ошибка «укажите фамилию».
- В журнале сервера после создания нет ФИО, даты рождения и диагноза.

### ТР-08. Оповещения

> «уведомление если выход за пределы диапазонов»

**Решено 2026-10-29:**
- Оповещения — записи в базе сервера; врач видит их у себя на панели.
- Оповещения получают и врач, и пациент. Пациенту — через синхронизацию.
- Оповещения — это «алерты», независимые от напоминаний, которые пациент настраивает сам (ТР-10).
- Пороги «высокий пульс» и «почти не ходит» — свои у каждого пациента, есть значения по
  умолчанию.
- Время дневных оповещений настраивается для каждого пациента в UTC. Выполнение нормы для
  прогресса и статистики считается по концу суток (ТР-03).

1. Сервер ДОЛЖЕН создавать оповещение `PatientAlert` в случаях:

   | Вид | Когда проверяется | Условие |
   |---|---|---|
   | **Высокий пульс** (`HighHeartRate`) | При приёме минут и «пульса сейчас» | Пульс > порога высокого пульса пациента |
   | **Норма дня не выполнена** (`DailyTargetMissed`) | Во время дневных оповещений | Норма дня (ТР-03) по данным на этот момент не выполнена |
   | **Норма дня выполнена** (`DailyTargetMet`) | Во время дневных оповещений | Норма дня по данным на этот момент выполнена |
   | **Почти не ходит** (`LowActivity`) | Во время дневных оповещений | Шагов за день < порога «почти не ходит» |
   | **Превышен порог тренировочных минут** (`TrainingMinutesExceeded`) | При каждом приёме минут и сразу при сохранении плана (сегодня) | Тренировочных минут за сутки > индивидуального верхнего порога |

2. **Время дневных оповещений** хранится в UTC (например, `17:00Z`). Оценивается день пациента
   (в его часовом поясе), в который попадает этот момент. Панель ДОЛЖНА показывать время и в
   поясе пациента: «17:00 UTC = 20:00 у пациента», чтобы врач видел, какой день оценивается.
3. Плановые дневные оповещения («норма дня выполнена / не выполнена», «почти не ходит») — по
   данным, пришедшим к моменту проверки. Поздние минуты меняют итог дня (ТР-03), но плановое
   оповещение за этот день повторно НЕ создаётся. *Предположение (В-16).* Превышение
   тренировочных минут проверяется отдельно по п. 12 и не блокирует плановую проверку.
4. «Почти не ходит» и «норма дня не выполнена» за один день создаются оба. *Предположение (В-16).*
5. **Высокий пульс:** минуты с пульсом выше порога подряд (без перерыва больше 5 минут) — один
   эпизод и одно оповещение с максимумом и длительностью. Проверяется при любой активности, не
   только при ходьбе. *Предположение (В-15).*
6. Повторная синхронизация тех же минут НЕ ДОЛЖНА создавать дубликат оповещения.
7. Дневные оповещения создаются только для дней программы; «высокий пульс» — всегда, пока
   приходят данные. *Предположение (В-01).*
8. Оповещение ДОЛЖНО содержать: пациента, вид, день или момент события (в поясе пациента),
   значения, по которым оно создано («пульс до 142 при пороге 130, 6 мин», «12 из 30 мин,
   6 200 из 10 000 шагов»), момент создания, просмотрено ли врачом.
9. **Врач:** список оповещений в карточке пациента и общий список по всем своим пациентам (новые
   сверху, фильтр по виду); отметка «просмотрено»; число непросмотренных — в списке пациентов
   (ТР-06). Оповещения не удаляются.
10. **Пациент:** телефон при синхронизации ДОЛЖЕН забирать новые оповещения и показывать их
    системным уведомлением Android (отдельный канал уведомлений «Оповещения клиники») и списком
    в приложении. Повторно одно оповещение не показывается.
11. Тексты НЕ ДОЛЖНЫ звучать как диагноз или призыв к экстренным действиям; тексты пациенту
    утверждает врач (В-19). На панели и в приложении ДОЛЖНО быть указано: оповещения приходят с
    задержкой синхронизации (до 30–60 мин) и не заменяют экстренную помощь.

12. **Превышение тренировочных минут** — дополнение из [d2.md](../d2.md), поведение согласовано
    2026-11-12:
    - Врач назначает индивидуальный верхний порог целым числом минут 1–1440, независимо от
      целевой нормы этапа, не в процентах. По умолчанию `null`: проверка отключена. Поле можно
      очистить для отключения. Отсутствие нового поля в старом PUT сохраняет назначенный порог.
    - Считать тренировочные минуты по ТР-02 за календарный день пациента (ТР-03). Проверять
      полный обновлённый итог каждого дня поступившего пакета, включая поздние и исправленные
      минуты, даже если новых записей нет. Равенство порогу не является превышением. Не ждать
      окончания суток или времени плановых оповещений. «Пульс сейчас» в итог не входит.
    - Настройки и нормы — версии соответствующего дня. Правка плана действует с сегодняшнего
      дня пациента и сразу запускает проверку его сегодняшнего итога. Вне дней программы
      превышение не проверяется: для таких дней не назначена тренировочная зона.
    - При первом обнаружении создавать одно оповещение на пациента и день: день, фактические
      минуты и порог на момент обнаружения. Последующий рост, уменьшение после исправления,
      повтор пакета или изменение порога не меняют и не удаляют эту историческую запись и не
      приводят к повторному уведомлению. Отметка просмотра сохраняется.
    - Оповещение доступно врачу в обоих журналах, фильтрах и непросмотренных счётчиках; пациенту
      — в журнале и системным уведомлением при синхронизации, один раз на `alert_id`.
      Превышение не отменяет выполнение нормы дня и не мешает другим оповещениям.
    - Старые телефоны не получают незнакомый вид: обновлённый клиент сообщает поддерживаемые
      виды через `supported_kinds`; без параметра сервер выдаёт только четыре прежних вида.

Части системы: Сервер (правила, журнал оповещений, планировщик дневных проверок, API для панели
и телефона), Панель (списки, отметка, настройки), Телефон (получение, уведомления, список).

Критерии приёмки (порог высокого пульса 130, «почти не ходит» 1 000 шагов, нормы 30 мин и
10 000 шагов, время оповещений 17:00 UTC, пациент в UTC+3):
- В 17:00 UTC (20:00 у пациента) за день 12 тренировочных минут и 6 200 шагов → одно
  оповещение «норма дня не выполнена: 12 из 30 мин, 6 200 из 10 000 шагов» у врача; у пациента
  — после ближайшей синхронизации.
- За день 35 минут и 11 000 шагов → «норма дня выполнена».
- За день 400 шагов → «почти не ходит» и «норма дня не выполнена».
- Пульс 135, 140, 138 в 10:01–10:03 и 131 в 10:06 → одно оповещение «высокий пульс: до 140, 6 мин».
- Те же минуты пришли повторно → новых оповещений нет.
- Врач отметил «просмотрено» → счётчик в списке пациентов уменьшился.

### ТР-09. Пульс в прямом режиме по запросу врача

> «Можно включить запись пульса прямым режимом с сервера на N минут.»

**Решено 2026-10-29:** запрос доставляется телефону через синхронизацию.

1. Врач ДОЛЖЕН на панели запросить «пульс сейчас» у своего пациента на N минут.
   *Предположение (В-11):* N — от 1 до 60, по умолчанию 10.
2. Телефон ДОЛЖЕН забирать запросы при синхронизации, включать непрерывное измерение и
   отправлять значения на сервер N минут, затем выключать. Запрос, который телефон забрал позже
   срока действия (по умолчанию 2 ч — *предположение*), не выполняется.
3. Пациент ДОЛЖЕН видеть на телефоне, что измерение включено по запросу клиники (постоянное
   уведомление), и мочь его остановить.
4. Панель ДОЛЖНА показывать состояние запроса: ожидает телефон, идёт, завершён, остановлен
   пациентом, не выполнен (браслет не найден, срок истёк) — и предупреждать: «телефон получит
   запрос при следующей синхронизации, обычно в течение 30 минут».
5. Запрос, полученный при открытом приложении (кнопка «Синхронизировать»), выполняется сразу.
6. **До кода — исследование (spike):** запуск непрерывного измерения из фоновой синхронизации
   требует foreground service типа `connectedDevice`; с Android 12 запуск такой службы из фона
   ограничен. Проверить на телефоне пациента и записать решение в ADR Android.

Части системы: Сервер (запросы, API), Панель (кнопка, состояние), Телефон (получение запроса,
фоновое измерение).

Критерии приёмки:
- Врач запросил 10 мин → панель «ожидает телефон» → после синхронизации «идёт», на панели
  значения каждые 2–3 с → через 10 мин «завершён», измерение на телефоне выключено.
- Пациент нажал «Остановить» → панель «остановлен пациентом».
- Телефон не синхронизировался 3 ч → запрос «не выполнен: срок истёк».

### ТР-10. Напоминания пациенту

> «Настройка частоты упоминаний пациентом.»

**Решено 2026-10-29:**
- Это напоминания пациенту; пациент настраивает их сам в приложении.
- Варианты частоты настраиваются, есть значения по умолчанию.
- Напоминания независимы от оповещений (ТР-08).
- Конкретное устройство — по лучшим практикам гибких систем напоминаний (источники ниже).

Принципы (из практик фитнес-трекеров и исследований мобильных вмешательств):
- **Напоминать по условию, а не по часам.** Напоминание приходит, только если пациент за
  интервал мало двигался (как «Reminders to move» у Fitbit: меньше 250 шагов за час, за 10 мин
  до конца часа). Двигался — напоминания нет.
- **Не утомлять.** Частые напоминания без пользы приводят к тому, что их перестают замечать или
  отключают: дневное окно, дни недели, предел в день, тишина после выполнения нормы, «отложить».
- **Управление у пациента.** Каждый вид — отдельный канал уведомлений Android: пациент может
  выключить его и в настройках системы.

1. Виды напоминаний (`ReminderKind`), каждый включается отдельно:

   | Вид | Когда | Условие | По умолчанию |
   |---|---|---|---|
   | **Пора пройтись** | В конце каждого интервала окна | Шагов за интервал меньше порога | вкл., интервал 1 ч, порог 250 шагов в час |
   | **Норма дня** | Один раз в заданное время | Норма тренировочных минут или шагов (ТР-03) ещё не выполнена: «осталось 12 мин и 3 000 шагов» | вкл., 18:00 |
   | **Наденьте браслет** | В окне, раз в интервал | Браслет снят больше 60 мин подряд (кроме зарядки) | выкл. |

2. Настройки напоминаний «Пора пройтись» и «Наденьте браслет»:
   - интервал: 30 мин, 1 ч, 1,5 ч, 2 ч, 3 ч;
   - окно: начало и конец (по умолчанию 09:00–20:00; окно не переходит через полночь, не короче
     1 ч);
   - дни недели (по умолчанию все);
   - порог шагов за интервал «Пора пройтись» — пропорционален интервалу (250 в час → 125 за 30 мин).
3. Общие правила:
   - не больше 8 напоминаний в день всех видов (*предположение*);
   - после выполнения нормы дня (ТР-03) «Пора пройтись» и «Норма дня» в этот день не приходят;
   - во время сна (тип активности `сон`) напоминания не приходят;
   - кнопка в уведомлении «Отложить на 30 мин»; в приложении — «Не напоминать сегодня»;
   - нет данных за интервал (браслет далеко, синхронизация не удалась) — «Пора пройтись» не
     приходит: по неизвестным данным не напоминаем. *Предположение (В-13).*
4. Перед проверкой условия телефон ДОЛЖЕН попытаться выгрузить свежие минуты с браслета
   (короткий фоновый сеанс, ADR-0003); не вышло — проверяет по тому, что есть.
5. Напоминания ДОЛЖНЫ работать без сервера и интернета. Настройки и факты показа на сервер НЕ
   передаются.
6. Технически (Android):
   - планирование — WorkManager или `AlarmManager.setWindow` с окном 10 мин; **без** точных
     будильников (`SCHEDULE_EXACT_ALARM`/`USE_EXACT_ALARM`): сдвиг на несколько минут для
     напоминания допустим, а точные будильники — особое разрешение, которое пациент может не дать;
   - разрешение на уведомления (`POST_NOTIFICATIONS`, Android 13+) спрашивается при первом
     включении напоминаний; без него — подсказка в настройках напоминаний;
   - расписание переживает перезагрузку телефона и смену часового пояса (окно — по местному
     времени телефона).

Части системы: Телефон.

Критерии приёмки (интервал 1 ч, окно 09:00–20:00, порог 250 шагов в час):
- 10:00–11:00 — 120 шагов → в ~10:50 «Пора пройтись».
- 10:00–11:00 — 900 шагов → напоминания нет.
- 21:00 — вне окна → напоминания нет.
- Норма дня выполнена в 15:30 → «Пора пройтись» после 15:30 не приходит, «Норма дня» в 18:00 тоже.
- Нажато «Отложить на 30 мин» в 10:50 → повтор в ~11:20, если условие ещё выполняется.
- Пациент выключил все напоминания → уведомлений нет; оповещения ТР-08 приходят как прежде.
- Девятое за день напоминание не приходит.

Источники:
- [Fitbit: Reminders to move](https://support.google.com/fitbit/answer/14225534) — условие 250
  шагов в час, напоминание за 10 мин до конца часа, окно и дни недели, по умолчанию 9:00–18:00.
- [Garmin: Move Alert](https://www8.garmin.com/manuals-apac/webhelp/forerunner70/EN-SG/GUID-B8FCDE89-3F2F-465F-AB0E-6FC9A6620E80-9242.html)
  — напоминание после часа неподвижности, сбрасывается ходьбой.
- [Android 14: точные будильники запрещены по умолчанию](https://developer.android.com/about/versions/14/changes/schedule-exact-alarms?hl=ru)
  — точные будильники только при необходимости, иначе `setWindow` (окно от 10 мин).
- [Reinforcement Learning to Send Reminders at Right Moments in Smartphone Exercise Application](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC8200090/)
  — без ограничения частоты напоминания начинают раздражать.

### ТР-11. Аккаунты врачей и доступ к пациентам

Не из `D.md`: нужно для ТР-07 — показывать ФИО и диагноз по общему ключу панели нельзя.

**Решено 2026-10-29:** у врача есть аккаунт, и он видит своих пациентов.

1. Каждый врач ДОЛЖЕН входить на панель под своим аккаунтом. Общий ключ панели
   (`KARDIO_DASHBOARD_KEY`) после ТР-11 НЕ ДОЛЖЕН давать доступа к данным пациентов.
2. У каждого пациента ДОЛЖЕН быть один лечащий врач. Врач ДОЛЖЕН видеть и менять данные только
   своих пациентов: карточку, программу, нормы, минуты, оповещения, запросы пульса.
3. Запрос к чужому пациенту ДОЛЖЕН отвечать так же, как к несуществующему (`404`), — не
   раскрывая, что пациент есть.
4. **Решено 2026-10-29 (В-23):**
   - вход — логин и пароль;
   - аккаунты врачей создаёт администратор сервера командой на сервере, интерфейса
     администратора пока нет;
   - передать пациента другому врачу может администратор той же командой;
   - пациенты, зарегистрированные с телефона по имени (демо, В-10), получают врача при
     регистрации по коду из QR v2; до этого их видит только администратор;
   - других ролей (медсестра, заведующий, который видит всех) пока нет.
5. Безопасность входа (лучшие практики, OWASP):
   - пароль — не короче 12 знаков, хранится только хешем Argon2id;
   - сеанс — cookie `HttpOnly`, `Secure`, `SameSite=Strict`; истекает через 8 ч неактивности
     (решено, В-23); «Выйти» завершает сеанс на сервере;
   - после 5 неудачных попыток входа подряд — задержка или временная блокировка входа;
   - пароль, cookie сеанса и хеш пароля не попадают в журналы.
6. Сервер ДОЛЖЕН записывать в журнал доступа, какой врач когда открывал карточку пациента и
   менял нормы (без ФИО и диагноза в записи — только идентификаторы). Нужно для разбора
   инцидентов с персональными данными (152-ФЗ).

Части системы: Сервер (контекст «Доступ» `features.access`, проверка доступа во всех
эндпоинтах панели), Панель (вход, выход, имя врача в шапке).

Критерии приёмки:
- Врач А вошёл → видит только пациентов А.
- Врач А открывает ссылку на пациента врача Б → «пациент не найден» (`404`).
- Неверный пароль 5 раз подряд → вход временно недоступен.
- Запрос к API панели без сеанса → `401`.
- Администратор передал пациента от А к Б → пациент пропал из списка А и появился у Б.
