# Утилита персонала — безопасность

Утилита — самое чувствительное звено проекта: в ней ключи **всех** браслетов клиники и вход в
аккаунт Xiaomi, к которому они привязаны. Ключ браслета даёт полный доступ к пульсу пациента
(данные о здоровье, особая категория персональных данных по 152-ФЗ).

## Что защищаем

| Актив | Где | Ущерб при утечке |
|---|---|---|
| Ключи браслетов (`AuthKey`) | База утилиты, шифротекст | Чтение пульса и истории пациента, перенастройка браслета |
| Пароль аккаунта Xiaomi | Только ввод на экране входа | Все ключи клиники, перепривязка браслетов |
| Сеанс облака (`ssecurity`, `serviceToken`) | Память ACL `platform.xiaomi` | Все ключи клиники до истечения сеанса |
| Содержимое QR (`PairingCode`) | Экран показа | Ключ одного браслета |
| Журнал выдачи | База утилиты | Кто из сотрудников когда выдал браслет (данных пациента нет) |

## Угрозы и меры

| Угроза | Мера | Где проверяется |
|---|---|---|
| Телефон потерян или украден | Ключи — AES-GCM ключом Keystore с `setUnlockedDeviceRequired` (ADR-0010); пароль и сеанс не хранятся; блокировка экрана на телефоне сотрудника обязательна (инструкция) | `SecretBoxTest` (androidTest), ревью |
| Резервная копия / перенос на другой телефон | `allowBackup=false`, `dataExtractionRules` исключают всё | Lint, ревью манифеста |
| Снимок экрана, запись экрана, превью в «Недавних» | `FLAG_SECURE` на экранах входа, браслета, QR | Ручная проверка (`adb exec-out screencap` даёт чёрный экран) |
| QR отправлен в мессенджер | Нет кнопок «Поделиться»/«Сохранить»; QR только на экране | Ревью |
| Ключ в журнале (logcat) | `toString()` секретов скрыт; архитектурный тест: `AuthKey`, `PairingCode`, пароль не в аргументах `Log.*`; hook агента блокирует вывод ключа | `:architecture`, hooks |
| Перехват трафика | Только HTTPS, `cleartextTrafficPermitted=false`, системные сертификаты, без своих `TrustManager` | Lint (`TrustAllX509TrustManager`), ревью |
| Вредоносная страница в WebView входа | WebView открывает только `account.xiaomi.com`; переходы на другие домены отклоняются; без `addJavascriptInterface`; cookies очищаются после входа | Тест `WebViewClient` (разрешённые хосты), ревью |
| Ключ в буфере обмена (ручной ввод) | После разбора буфер очищается (`clearPrimaryClip`, API 28+); поле ключа — `KeyboardType.Password`, без подсказок клавиатуры | Ревью |
| Ключ в тестах и коде | Только синтетические fixtures, включая `00112233445566778899aabbccddeeff` и общий QR fixture `0123456789abcdef0123456789abcdef`; настоящие — нигде в репозитории | Hook, ревью |
| Прежний пациент сохранил ключ (ключ при возврате не меняется) | П2 (ADR-0011): сотрудник просит удалить приложение при возврате (напоминание в С6); сервер не принимает минуты после закрытия выдачи — этап 2 | Остаточный риск до этапа 2 принят |
| История прежнего пациента на браслете уходит врачу нового | П1 (ADR-0011): приложение пациента выгружает только минуты после сканирования QR | Тест `HistorySyncStart` |
| Подмена приложения | Release подписывается ключом клиники; ключ подписи вне репозитория; установка — только из доверенного источника клиники | Процедура выпуска |

## Правила для кода

- Секреты — value-типы с `toString()` без значения; в `data class` с секретом — свой `toString()`.
- Ключ браслета расшифровывается **только** в момент проверки и показа QR и не кешируется в
  `UiState` дольше показа экрана; `UiState` с секретом не логируется.
- Пароль — `CharArray`/`String` только в `UiState` экрана входа; после попытки входа поле очищается.
- Сеанс облака — поле объекта ACL, без записи на диск, без `SavedStateHandle`.
- Журналы `KardioStaff`/`KardioCloud`: адрес браслета можно, ключ, пароль, токены, cookies,
  тела ответов облака — нельзя.

## Band 9 и QR v3

- QR v3 содержит тот же секрет в Base64url, **не шифрует** его. `FLAG_SECURE`, таймер,
  запрет share/save и скрытый `toString()` действуют без изменений.
- v3 не содержит MAC с двоеточиями или raw hex32: старый permissive reader не должен
  принять Band 9 как Band 6. Неизвестный protocol закрывает подключение и QR.
- SQLite schema 3 добавляет несекретный protocol к inventory/checks/issuances; sealed keys,
  alias Keystore и схема шифрования не меняются. Миграции старых строк — только Band 6.
- Чтение не создаёт отсутствующий alias Keystore. Ошибка расшифровки блокирует QR/проверку,
  не удаляет шифротекст и не мешает чтению несекретного реестра. Сначала разблокировать телефон;
  если ошибка повторяется — администратор восстанавливает ключ из доверенного источника,
  не очищая приложение. Запрещены автоматическая замена ключа, reset или перепривязка.
- Ручной ввод принимает один hex-ключ либо строгий QR v1 Band 6 / v3 с тем же выбранным MAC
  и протоколом. Неизвестный/повреждённый QR не получает свободный regex-fallback. QR с полями
  регистрации пациента отклоняется: их нельзя молча потерять при импорте ключа в инвентарь.
- Перед записью выдачи повторно проверяются текущий ключ, протокол и свежесть последней проверки.
  Уход QR-экрана в фон закрывает код и отменяет незавершённую подготовку/подтверждение.
  Таймер и `FLAG_SECURE` остаются обязательными; содержимое QR в saved state не записывается.
- Band 9 выбирается явно из bonded Classic/Dual устройств; имя не является доказательством.
  Ни pairing/unpairing, ни fallback в Huami, ни SET 8/11, ни history ACK 8/5 не вызываются.
- Production client допускает только HMAC-auth и точную M2345B1 / 2.3.98. Отмена/ошибка закрывает
  socket; scoped копия auth key очищается. Нет raw-пакетов/nonce/session keys в staff logs.
- История, live start/stop и today steps заблокированы: отсутствие доказанной семантики не
  подменяется sample/0, успешное read-only чтение не подтверждает готовность мониторинга.

## Чего утилита не делает

- Не отправляет ключи на сервер клиники (открытый вопрос 2 сервера).
- Не хранит данные пациентов (открытый вопрос 1 в [README.md](README.md#открытые-вопросы-решает-человек-до-кода--не-додумывать)).
- Не отвязывает браслеты в облаке: это делает ключ недействительным у пациента.
