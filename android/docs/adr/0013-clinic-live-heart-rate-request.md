# ADR-0013: Пульс по запросу клиники — CDM и foreground Worker

- Статус: принято; исследование на устройстве выполнено (2026-11-01)
- Дата: 2026-11-01

## Контекст

ТР-09 требует, чтобы телефон при синхронизации получил запрос врача, включил непрерывное
измерение на 1–60 минут и показывал постоянное уведомление с действием «Остановить». Обычный
короткий `HistorySyncWorker` может подключиться к BLE в фоне, но процесс и соединение не
гарантированы на всю длительность. С Android 12 приложение в фоне не может произвольно поднять
foreground service; Android 14+ также требует тип службы и отдельное разрешение типа.

До реализации проведён spike на телефоне пациента Samsung SM-S731B, Android 17 (API 37),
`targetSdk 36`. Временный debug-only `CoroutineWorker` вызывал `setForeground` с типом
`connectedDevice`, открывал общий `BandConnection` и собирал `ActivitySource.liveHeartRate()`.
После исследования временный код и тестовая CDM-ассоциация удалены; данные приложения не
очищались.

Результаты:

- после недавней видимой Activity Worker поднял `SystemForegroundService` типа
  `connectedDevice`;
- из полностью фонового приложения без Companion Device Manager (CDM) Android отклонил запуск:
  `ForegroundServiceStartNotAllowedException`, причина `DENIED`;
- при CDM-ассоциации тот же запуск из force-stopped процесса разрешён, системная причина —
  `COMPANION_DEVICE_MANAGER`;
- при выключенном экране браслет авторизовался, непрерывный поток выдавал реальные значения
  каждые 2–3 секунды и завершился по длительности;
- действие уведомления отменило Worker, остановило BLE и `SystemForegroundService`;
- при запрещённом `POST_NOTIFICATIONS` FGS работал, но пациент не видел постоянного уведомления
  и не мог остановить измерение из шторки; при разрешении уведомление и действие были видны;
- общий `BandConnection` последовательно выполнил одновременную синхронизацию истории и затем
  измерение, второго GATT-соединения не возникло.

## Решение

1. Браслет ассоциируется через системный `CompanionDeviceManager` после QR-привязки. Для уже
   привязанных браслетов приложение предлагает одноразовую системную привязку до включения
   запросов клиники. Ассоциация — обычная BLE, с фильтром по адресу; если браслет не рекламируется,
   пациенту предлагается разбудить его и повторить. Обхода системного подтверждения нет.
2. Приложение объявляет `REQUEST_COMPANION_START_FOREGROUND_SERVICES_FROM_BACKGROUND`,
   `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_CONNECTED_DEVICE` и тип `connectedDevice` для
   `androidx.work.impl.foreground.SystemForegroundService`.
3. Запрос выполняет отдельный long-running `CoroutineWorker`, повышенный через `setForeground`.
   Он использует единственный `BandConnection.withSession(isBackground = true)`, публикует
   значения в существующий `LiveHeartRateFeed` и прекращает работу по длительности или отмене.
4. Параллельное ручное и клиническое измерение координирует один application-level контроллер.
   Он владеет единственным потоком измерения; ViewModel больше не владеет BLE-корутиной.
5. Запросы забираются после **каждой попытки** ручной или периодической синхронизации, даже если
   новых минут нет или выгрузка истории с браслета не удалась. Для этого вводится отдельное
   событие завершения попытки синхронизации, не зависящее от `ActivityHistory.changes`.
6. Идентификатор принятого запроса и неотправленные изменения состояния хранятся устойчиво.
   Повторная доставка не запускает второй Worker, а отчёт о состоянии повторяется до успеха.
7. До запуска требуется разрешение уведомлений. Если пациент его запретил, измерение не
   начинается, сервер получает «не выполнен: уведомления запрещены», а приложение объясняет,
   как включить разрешение. Невидимое пациенту клиническое измерение запрещено.
8. Уведомление сообщает, что измерение запросила клиника, показывает оставшееся время и действие
   «Остановить». Действие отменяет Worker и отправляет состояние `stopped_by_patient`.
9. WorkManager может отложить доставку команды и расходует квоту JobScheduler на Android 16+.
   Максимум 60 минут и редкий пользовательский запрос приемлемы; запуск не объявляется
   мгновенным. Если эксплуатационные замеры покажут нехватку квоты, отдельный прямой FGS будет
   новым ADR.

## Последствия

- Фоновый запуск возможен только после явного системного согласия пациента на CDM-ассоциацию.
- Запрос врача не обходит Android-ограничения и всегда видим пациенту.
- При отсутствии CDM, разрешения уведомлений или браслета сервер получает понятный терминальный
  результат, а не бесконечное состояние «ожидает».
- Существующая отправка значений `LiveHeartRateSharing` переиспользуется; второй канал данных не
  появляется.
- Запрос, полученный при ручной синхронизации, ставится сразу; периодический — при следующем
  запуске WorkManager, обычно до 30 минут, но без гарантии точного срока.

## Отвергнутые варианты

- Запуск `connectedDevice` FGS из обычного фонового Worker без CDM — отклонён Android 17.
- Только `holdOpen` в ViewModel — не защищает процесс и недоступен фоновой синхронизации.
- Постоянный foreground service — лишний расход батареи между запросами.
- Непрерывное измерение без разрешения уведомлений — пациент не видит его и не может остановить.
- Второе BLE-соединение для запроса — нарушает ADR-0003 и ограничение браслета.
- Exact alarm или push как обход — не нужны для принятой доставки опросом и меняют требования.
