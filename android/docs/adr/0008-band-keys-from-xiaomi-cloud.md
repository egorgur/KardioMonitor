# ADR-0008: Ключи браслетов — из облака Xiaomi под аккаунтом клиники

- Статус: принято (2026-10-29)
- Дата: 2026-10-29

## Контекст

Ключ авторизации браслета выдают серверы Xiaomi при привязке в Mi Fitness (или Zepp Life);
создать его нельзя ([ble-protocol.md](../ble-protocol.md#ключ-авторизации)). Сейчас сотрудник
достаёт ключ через `adb` из логов Mi Fitness или скриптом на ноутбуке (`tools/zepplife_key.py`,
`huami-token`) и печатает QR скриптом `tools/make_qr.py`. Это требует ноутбука, Python и
навыков разработчика.

С Android 11 приложение не может читать файлы другого приложения в `Android/data`, поэтому
чтение логов Mi Fitness из утилиты невозможно.

## Решение

Утилита получает список браслетов аккаунта клиники и их ключи из облака — тем же способом,
что `huami-token` (MIT, © Kirill Snezhko) и `tools/zepplife_key.py`. Протокол облака —
[staff-app/xiaomi-cloud.md](../staff-app/xiaomi-cloud.md).

1. **Mi Fitness (основной путь).** Вход в аккаунт Xiaomi (`sid=miothealth`) → `ssecurity`,
   `serviceToken` → подписанный и зашифрованный запрос `get_source_list` → MAC и `auth_key`.
2. **Zepp Life (запасной путь).** OAuth-вход в аккаунт Xiaomi во встроенном WebView →
   токен Huami → список устройств с `auth_key`.
3. **Ручной ввод** MAC и ключа — всегда доступен (ключ получен из логов на ноутбуке).

Правила:

- Облако — чужая модель: весь обмен — в ACL `platform.xiaomi` модуля `:staff`; наружу —
  доменный порт `BandKeySource`, ошибки — `sealed`-результат.
- Пароль аккаунта не сохраняется. Сеанс облака (`ssecurity`, `serviceToken`, токен Huami)
  живёт только в памяти процесса. Подробно — [staff-app/security.md](../staff-app/security.md).
- Криптография облака (RC4, подписи, nonce) — только с тестами на эталонных значениях,
  полученных скриптом из `huami-token` (как ADR-0005/`Huami2021Test` для браслета).
- В KDoc перенесённых функций — ссылка на источник и лицензию MIT; текст лицензии — в
  `staff/src/main/assets/licenses/huami-token.txt` и на экране «О программе».

## Последствия

- Сотруднику не нужен ноутбук: привязал браслет в Mi Fitness — получил ключ в утилите.
- Зависимость от неофициального API Xiaomi: смена протокола входа или шифрования ломает
  получение ключей (но не работу пациентов — у них ключ уже в QR). Запасные пути: Zepp Life
  и ручной ввод.
- У аккаунта клиники двухфакторной защиты нет (решение человека, 2026-10-29) — основной вход
  Mi Fitness паролем. Xiaomi всё равно может потребовать подтверждение (капча, вход с нового
  устройства): сотрудник увидит понятную ошибку, подтвердит вход в Mi Fitness на этом телефоне
  и повторит, либо возьмёт ключ через Zepp Life или вручную.
- Если клиника включит 2FA, вход паролем перестанет работать — сначала исследование входа
  через WebView ([xiaomi-cloud.md](../staff-app/xiaomi-cloud.md#если-включат-2fa)), затем
  дополнение к этому ADR.

## Открытые вопросы

1. Какой регион аккаунта клиники (`ru`, `de`, `sg`…) — от него зависит заголовок
   `region_tag`. Выясняется в шаге 3 плана.

Снят 2026-10-29: вход через WebView с 2FA — у аккаунта клиники 2FA нет, исследование не нужно.

## Отвергнутые варианты

- Чтение логов Mi Fitness на телефоне сотрудника — запрещено scoped storage (Android 11+).
- Свой сервер-посредник для облака Xiaomi — пароль аккаунта клиники попал бы на сервер.
- Только ручной ввод — оставляет ноутбук и `adb` в процессе выдачи.
